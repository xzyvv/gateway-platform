## 2. 三条失败门禁的定性

### 2.1 clippy `await_holding_lock` — 真实违规，且暴露隐性依赖

**不是误报。** 精确表述：

- `runtime/gateway.rs:635` 的 `if let Some(old) = self.bus_managers.lock().get(&name).cloned()` 中，临时 guard 的**借用期**跨越了 `.await` 点。
- `.cloned()` 完成后 guard 已不再被借用，**await 时并不实际持锁**；clippy 报的是「借用期跨越 await」。
- 但**本仓能编译通过，靠的是第三方 crate 传递性开启了 `parking_lot` 的 `send_guard` feature** —— 来源为 `async-opcua-client/core/server v0.19.0`（`cargo tree -e features -i parking_lot --workspace` 输出：`parking_lot feature "send_guard" ← async-opcua-*`）。
- 独立探针实证：不启用 `send_guard` 时，同一写法被 rustc 拒绝 —— `future cannot be sent between threads safely ... MutexGuard ... which is not Send`。

**结论**：真实架构债 + 门禁债（编译通过与否取决于第三方依赖树的传递 feature）。定级 P1（登记为 DD-05）—— 不是 P0，因为 `parking_lot` guard 跨 await 不会 panic。

**注意**：本仓 `south/scheduler/mod.rs:21-48` 的 LOCK ORDER 表已明文写「如必须反序…请改用 `tokio::sync::Mutex` 显式 await，或提取快照临时变量（先 clone 出值再释放锁、再去 await 锁路径）」——本处正是反例，修复方向文档里已经写好。

### 2.2 vue-tsc 4 处错误 — 真实契约漂移，非绑定未重生成

**已排除「ts-rs 绑定过期」这一可能**：先执行 `npm run types:export`（成功），再执行 `npm run type-check`，**错误依旧**。

**根因是 ts-rs 对 `Option` 的映射口径不统一**：

| 字段 | Rust 声明 | ts-rs 属性 | 生成结果 |
|---|---|---|---|
| `timeout_ms` | `pub timeout_ms: Option<u64>` + `#[serde(default)]` | `#[ts(type = "number")]` | `timeout_ms: number`（**必填**） |
| `write_min` | `pub write_min: Option<f64>` | `#[ts(optional)]` | `write_min?: number`（可选） |

同一份 `PointConfig` 里两种写法并存，生成结果对「可空」的表达不一致。前端 4 处按「可选」使用 → 报错：

- `gateway-web/src/composables/devices/usePoints.spec.ts:83`
- `gateway-web/src/utils/pointDefaults.ts:34`
- `gateway-web/src/views/points/dialogs/PointsBatchEditDialog.spec.ts:44`
- `gateway-web/src/views/points/dialogs/PointsCopyDialog.spec.ts:35`

定级 P1（DD-06）。

### 2.3 chaos 5 例失败 — 仓库自带的陈旧桩与陈旧断言，非本次引入

**稳定可复现**：单场景重跑 `cargo test -p gateway-core --test chaos -- scenarios::scenario_modbus_tcp_roundtrip --exact` 仍失败（0 passed / 1 failed），排除并行干扰与偶发因素。

**三类根因**：

| 根因 | 影响用例 | 证据 |
|---|---|---|
| **测试桩回帧 unit_id 写错** | `scenario_modbus_tcp_roundtrip`、`scenario_modbus_tcp_concurrent_responses_routed_by_tx_id`、`scenario_network_switch_reconnects_and_resumes` | `gateway-core/tests/chaos/harness.rs:275` 把 `pdu.first()`（= 功能码）当 unit_id 回填；请求的真实 unit_id 在 `header[6]`。客户端期望 1、实收 3 → `Malformed("unit_id mismatch: expected 1, got 3")`。桩在 `ab44c3d`（2026-11-20）为响应加 unit_id 校验后失效，此前被掩盖 |
| **断言陈旧 - BACnet** | `scenario_bacnet_ip_rpm_and_write_property` | `ae827f2` 把 WriteProperty 的 Abort/Error/Reject 归为「确定未生效 → 可安全重试」，实现改为 `CollectorError::DeviceRejected`（`bacnet/frames/write.rs:139-143`）；场景仍断言旧的 `InvalidFrame`（`scenarios.rs:2693-2694`） |
| **断言陈旧 - 串口写** | `scenario_serial_modbus_rtu_write_family` | `ae827f2` 统一写语义后，「已下发无应答」由 `NoReply` 改判 `WriteUncertain`（`modbus/trait_impl.rs:28-29`）；场景仍断言 `NoReply`（`scenarios.rs:2620-2622`） |

**影响面**：`.github/workflows/heavy.yml` 的 `chaos` 作业会失败；`release-gate.yml` 无条件调用 heavy.yml → **打 tag / 手动触发 / 每周定时发布门禁全部红**。定级 P0（DD-04）。

**修复范围**：仅测试代码与断言注释，不改生产逻辑。

## 3. 门禁补强建议

> 以下均为**补全现有门禁能力**，不新增功能面。

### 3.1 P0 — 立即修

| 项 | 建议 | 对应债务 |

### 3.2 P1 — 纳入常规门禁

| 项 | 现状 | 建议 |
|---|---|---|
| clippy | CI 快门禁 `check` 走 `gateway-core/scripts/ci.sh`（内含 clippy 自带 `-D warnings`），但当前仓库有 1 处违规 → **该门禁实际处于失败态** | 修掉 DD-05 后即可恢复；建议在修复合入前**不要**把 clippy 结果视为已通过 |
| vue-tsc | `npm run type-check` **已在快门禁中**（`.github/workflows/ci.yml:327-328`，显式跑 `vue-tsc --noEmit` 单独拦类型错误） | 该门禁**当前为红**（4 处 `timeout_ms` 契约漂移）；需先修 DD-06 才能恢复绿 |
| 前端类型绑定一致性 | `ci.yml:282-292` 已有「Verify ts-rs bindings are up to date」（用 `git status --porcelain` 捕获新增未跟踪 `.ts`） | 该检查覆盖「绑定未提交」，**不覆盖「绑定内容与后端语义是否一致」**——本次 4 处错误正是绑定已提交、但语义漂移（DD-06），该门禁无法拦截。补强方向见 §3.3 |
| chaos | 属重作业：`ci.yml:384-405` 的 `heavy` 作业（`needs: check`）调用 `heavy.yml`，触发路径为 push 到 main / `workflow_dispatch` / `RUN_HEAVY=true`；`release-gate.yml:46-54` 亦复用 `heavy.yml`（触发：`workflow_dispatch` / `v*` tag / 每周一 03:17 cron） | 修完 DD-04 前，发布动作必须知道该作业是红的；修复后建议在 `release-gate.yml` 的结论步骤显式列出 chaos 结果 |
