## 2. 清单主体（按 ROI 从高到低）

### 🟢 A 档：立刻能做，小投入、高回报

#### 1. DD-48 · 从站扫描失败别再弹「扫描完成」
- **现在的毛病**：`SlaveScan.vue:159,169` 不管成功失败都 `ElMessage.success("扫描完成…")`，同时 `:164,174` 又把失败原因写进常驻 `scanError`——成功 toast 和失败提示同屏。
- **现场会看到什么**：扫不到设备时先弹绿色「扫描完成，发现 0 台」，运维以为扫完了，下方红色失败提示容易被当成附带信息。属「把失败报成成功」，与已修的 DD-02/DD-03 同类。
- **工作量**：**极小**（<0.5 天）。把成功 toast 收进成功分支 + 补 1~2 条组件测试。
- **价值**：**中高**。消除现场最易误判的一类提示；口径与已建立的「终态显式」一致。
- **ROI 判断**：工作量几乎为零、零回归风险，性价比全场最高。
- **依赖**：无。
- **验收**：失败场景不出现 success toast；成功场景 toast 保留。

#### 2. DD-27 · 删掉前端幽灵会话 `s3`
- **现在的毛病**：`usePacketReplay.ts:30` 的 `BUILTIN_IDS` 含 `s3`，后端 `sessions.rs` 只内置 `s1`/`s2`。
- **现场会看到什么**：点开 `s3` 内置示例必然 404——一个必现的功能死角，只是低频。
- **工作量**：**极小**（<0.5 天）。前端移除 `s3`，补一条「内置 ID 与后端一致」的断言。
- **价值**：**中**。必现 bug 但使用频率低。
- **ROI 判断**：改 1 行 + 1 测试，无脑先清。
- **依赖**：确认后端短期不会补 `s3`（当前注释明确只 s1/s2）。
- **验收**：内置会话下拉不再出现 s3；isBuiltin('s3') 为 false。

#### 3. DOC-F1 · 修正测试 README 的过时数字
- **现在的毛病**：`src/test/README.md:4` 写「35 个 spec / 266 用例 / e2e 6 条」，实测 **256 个 spec / e2e 4 个文件**；`frontend.md:102` 也写「6 条只读核心链路」。
- **现场会看到什么**：不直接影响现场，但接手人会按 35 个估算维护成本，严重低估；也说明文档自某次大规模补测后失修。
- **工作量**：**极小**（<0.5 天）。改成不写死动态数字，或接入脚本生成。
- **价值**：**中高**。零风险、防误判，与既有 ROI-03「文档销账」同类。
- **ROI 判断**：纯文档、零副作用，可随时插入。
- **依赖**：无。
- **验收**：文档数字与实测一致，或改为无静态数字的表述。

#### 4. DD-30 · 报文编辑页写帧加二次确认
- **现在的毛病**：`PacketEditor.vue:116-135` 的 `send()` 只校验 HEX 合法性就直接下发；同域 `StepDebug.vue:71,198,216-217` 已有 `isWriteFrame()` + `confirmAction()`。
- **现场会看到什么**：在生产总线上误填一帧写命令，点发送即真实下发，缺少单步调试页已有的安全兜底。
- **工作量**：**小-中**（1~2 天，若抽共享 composable）；**小**（0.5~1 天，若直接复用 StepDebug 现成函数）。
- **价值**：**高**。全部 7 项里唯一涉及「误操作产生真实后果」的，安全兜底。
- **ROI 判断**：价值最高，工作量可控（有现成实现可抄），排 A 档末位仅因其余三项是半天级。
- **依赖**：无。复用 StepDebug 逻辑，不新增功能面。
- **验收**：写帧（如 FC06/FC16）下发前弹确认；读帧不受影响。
- **状态**：✅ 已完成（2026-11-23）。把 StepDebug 内联的 `isWriteFrame` 抽到 `utils/hexFrame.ts`（FC05/06/15/16，口径对齐后端 `judge_modbus`），两页共用；PacketEditor `send()` 写帧前调 `confirmAction`（`autofocus:false` 防习惯性回车误发）。补 `hexFrame.spec.ts`（含"从站地址恰好是 05/06 不得误判"）与 PacketEditor 三条确认用例。type-check/lint/相关 spec 全过。

### 🟡 B 档：值得做，投入中等

#### 5. DD-28 · DLT645 内置示例帧校验和 — ✅ 已完成（2026-11-23）
- **复核结论**：**问题属实**。解析器 CS = 整帧除末两字节累加和 & 0xFF（frameParser.ts:186），对示例 `68 AA×6 68 11 04 33×4` 逐帧算得 `0xAD`，而帧内写 `0x0E`；旧清单数字准确。
- **现场表现**：内置示例在解析页显示「校验和失败」，用户误以为解析器坏了。注意 `parseDLT645` 整体 `valid` 不看校验和，只在字段里标红，属于字段级误导。
- **实际改动**：`utils/frameParser.ts` 示例帧 CS `0E` → `AD`（附 DD-28 注释）；`frameParserError.spec.ts` 的「示例帧完整性」块新增回归钉子，直接按字节复算 CS 并断言解析器判「通过」。
- **验收**：相关 spec 12/12 通过；未改判帧逻辑。
- **工作量 / 价值**：小 / 中（复核 + 修正 + 补测试）。

#### 6. DOC-F2 · 补项目 README 的工程说明 — ✅ 已完成（2026-11-23）
- **实际改动**：`gateway-web/README.md` 从 13 行扩为完整工程说明——快速开始（Node 22 要求、env 配置、端口与代理）、常用命令表、测试分层（单测 / E2E 隔离网关 / 类型契约）、目录结构指针、环境变量表、相关文档链接；**保留原「优化方向」章节**。
- **反漂移设计**：spec / e2e 数量不写死，指向实测命令与权威文档（落实 DOC-F1 的教训）。
- **验收**：新人仅凭根 README 可跑起 dev/build/test/lint/e2e。
- **工作量 / 价值**：小 / 中（零风险）。

### 🟠 C 档：价值明确但改动面大，可延后

#### 7. DD-47 · 收敛三套字节工具为单一实现 — ✅ 已完成（2026-11-23）
- **原问题**：`hexToBytes` 在 `hexDump.ts:16` / `frameParser.ts:23` 各一份（且口径不同：前者非法返回 `[]`，后者奇数抛错、非 hex 产生 **NaN**），`hexFrame.ts` 另有 `normalizeHex`/`isValidHex`。
- **实际改动**：新建 `utils/hexCodec.ts` 作为唯一真源，收拢 `hexToBytes` / `normalizeHex` / `isValidHex` / `isWriteFrame`（DD-30 已抽出的）/ `byteToAscii`；`hexFrame.ts` / `hexDump.ts` 改为 re-export，`frameParser.ts` 删除本地私有实现改 import。**对外符号与调用方 import 路径全部不变**。
- **口径选择**：统一为「非法输入返回空数组」——展示层不中断；解析层三个 parse 函数本就有 `bytes.length < N` 检查，空数组落到「帧长度不足」的合理降级，同时消除了非 hex 产生 NaN 的隐患。保留「去 0x 前缀」的宽容特性。
- **验收**：新建 `hexCodec.spec.ts`（10 条，含"旧入口与单一真源同符号等价"钉子 + NaN 回归）；相关 43/43 通过，帧解析逐字节结果不变。
