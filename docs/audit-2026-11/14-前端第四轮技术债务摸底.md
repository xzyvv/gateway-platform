## 3. 不做清单（本轮核实为健康，明确不建议改动）

> 防止后续有人拿扫描结果当债来修——这是本轮最重要的产出。

| 疑似项 | 为什么不是债 |
|---|---|
| 生产 8 处 `as unknown as` | 全是「运行时已守卫 + 编译期补类型」：`sanitizeForLog` 递归处理 unknown 值、`responseInterceptor` 的 wrapper 结构断言、`performance.memory`（Chrome 非标准 API，前面有 `hasMemoryAPI()` 守卫）；`crud.ts` / `DeviceImportBranch.vue` 的 `as unknown as DeviceConfig` 是表单 reactive → DTO 边界强转，字段来自 `formRef.validate()` 校验过的表单，且有归一化注释 |
| 215 个 `el-button` 无显式 `type` | Element Plus 的 `el-button` 默认 `native-type="button"`，不会在 form 内误触发 submit；显式声明属于风格偏好，非缺陷 |
| 4 个 `<style src="...">` 非 scoped | 外链 CSS 用命名空间选择器（`.sidebar` / `.lic-*` / `.header`），注释明确说明要穿透 Element Plus 内部类、`:deep()` 在非 scoped CSS 中无效——是有意设计 |
| 121 处 `!important` | 52 处在 global.css（全局覆盖基线）、25 处在 Sidebar.css（穿透 EP 组件内部），其余分散且带具体场景，非样式失控 |
| 诊断导出等场景的裸 `Promise.all` | 每个并发调用都挂了 `.catch(()=>undefined/[])` 降级，Promise.all 不会整体拒绝——这是「尽量多导出」的有意设计，与项目 `runConcurrent` / `allSettled` 范式并存 |
| `PointsCopyDialog.vue:6` v-for「缺 key」 | 脚本误报：`:key="d.id"` 实际在第 8 行，箭头函数 `=>` 的 `>` 提前截断了脚本的标签匹配。真实缺 key 数为 0 |
| HubShell.vue 493 行等大组件 | 全部在 800 行预算内（用户已拍板选 A，见项目 MEMORY.md），无拆分必要 |
