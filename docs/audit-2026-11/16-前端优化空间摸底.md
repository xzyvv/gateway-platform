## 2. 真优化点：错误展示层收敛不完整（P3 · 语义/体验债）

### 2.1 证据链

**第一层——拦截器的全局提示策略**（`src/api/http/responseInterceptor.ts`）：

```
84: notify.error(message, { code, traceId, silent: isMutation && !isGlobalAlert })
93: if (!isMutation || isGlobalAlert) markUserNotified(bizError)
...
236: notify.error(`请求失败(${status}): ${msg}`, { ..., silent: isMutation })
238: // 仅当真的弹了（GET；写操作是静音的，提示归页面 catch 负责）才标记
239: if (!isMutation) markUserNotified(error)
```

GET 失败 → 全局通知 + `USER_NOTIFIED` 标记；写操作失败 → 静音，由页面 catch 负责。

**第二层——统一出口的设计意图**（`src/composables/core/useErrorDisplay.ts:85-90`）：

```ts
function showToast(err: unknown, action?: string): void {
  // 全局层（HTTP 拦截器）已经弹过同一条错误的通知时不再重复弹
  if (isUserNotified(err)) return
  ElMessage.error(message(err, action))
}
```

同文件 `:77-82` 的 `message()` 还会拼 `withDiagHint`（诊断建议），注释 `:75-76` 明确"诊断建议收敛到 message() 统一拼，三种展示风格走同一文案"。

**第三层——实际调用绕过了统一出口**（`src/composables/config/useConfigVersions.ts:40-49`）：

```ts
async function load() {
  try {
    versions.value = await listConfigVersions()   // GET
  } catch (e) {
    ElMessage.error(failureMessage('加载版本列表', e))  // 直接弹，未走 showToast
    logError('cfg-ver', e)
  }
}
```

`failureMessage`（`src/utils/errorHandler.ts:88`）的文档明确写"**写操作失败提示**：写操作的全局弹窗被拦截器静音，页面 catch 是用户看到失败原因的唯一出口"。而 `load()` 是 GET 读操作——把它套在 GET 上，就同时踩中两个问题：

1. **重复提示**：拦截器已弹全局通知并标记，页面 catch 再弹一条 → 用户看到两条。
2. **丢失诊断建议**：`failureMessage` 不含 `withDiagHint`，与该 composable 自身 `showToast` 宣称的"统一拼诊断建议"不一致。

### 2.2 规模

脚本统计（排除 spec）：`ElMessage.error` 共 113 处，其中 **84 处位于错误处理上下文**（含 `catch` / `extractErrorMessage` / `failureMessage` / `message(...)`）。剩余约 29 处是业务校验提示（如"请先选择设备"），直接 `ElMessage.error` 合理，不在优化范围内。

84 处中，写操作（mutation）用 `failureMessage` 是正确的（全局静音，页面是唯一出口，不会重复）；**读操作（GET）直接弹才构成重复提示**。典型涉及：

| 文件 | 动作 | 操作类型 |
|---|---|---|
| `useConfigVersions.ts:45` | 加载版本列表 | GET |
| `useConfigVersions.ts:72` | 加载快照 | GET |
| `useAutoDetect.ts:67/86` | 获取探测进度 / 启动探测 | 需逐个核对 |
| `useRegisterScan.ts:248` | 删除扫描记录 | 写操作（正确） |
| `BusPauseBanner.vue:81/95` | 暂停/恢复总线 | 写操作（正确） |

### 2.3 建议

把**读操作 catch** 的 `ElMessage.error(...)` 换成 `showToast(e, '<动作>失败')`（或需要行内错误条时用 `showInline`），即可自动获得去重 + 诊断建议 + 统一文案，无需改拦截器。

**边界与风险**（必须逐处核对，不可全局替换）：

- 写操作 catch 保持 `failureMessage` 或迁移到 `showToast` 均可（后者文案一致且多诊断建议），但**不要在写操作上依赖去重**——写操作没有 USER_NOTIFIED 标记。
- 带追加文案的场景（`useConfigVersions.ts:283` 的「…；已取消保存」、`:337` 的「…；重启网关后将按新配置运行」）需要保留，或扩展 `showToast` 支持后缀。
- `showToast` 会跳过已被标记的 GET 错误；若某页面依赖"即使全局弹过也要本地再提示"的强反馈，应改用 `showInline`（它保证行内文案一定写入）。

## 3. 已优化清单（核实为健康，明确"不做"）

### 3.1 请求治理

`src/api/inflight.ts` 是教科书级的注册中心：256 上限、触顶**跳过登记而非 abort 正常请求**（BUG W-3 修复）、listener 快照遍历防重入、超限计数诊断。AbortController 在 12 个文件中用于切网关/登出/扫描/登录等场景的取消。

### 3.2 错误恢复

`PageErrorBoundary.vue` 的三层分工清晰：`onErrorCaptured`（组件同步错误）+ `app.config.errorHandler`（应用兜底）+ `window.unhandledrejection`（异步拒绝），互不冲突。降级卡片带重试、刷新整页、复制错误堆栈（走 clipboard 回退），`role="alert"` + `aria-live` 无障碍到位。

### 3.3 请求竞态

`useRequestGuard` 在 dashboard / history / devices / system / simulate 等 20+ 处使用，用序号语义只接受最新响应；配套 `useUnmountedGuard` 管卸载作废，职责分离明确。

### 3.4 错误格式化工具是分层，不是重复

`extractErrorMessage`（底层提取，72 次）→ `composeFailure`（拼装，5 次）→ `failureMessage`（中层，19 次）→ `useErrorDisplay.message`（加诊断建议）→ `showToast`（去重后展示，89 次）。每层有明确职责和文档，不是重复实现。

## 4. 误报清单（防止后续误改）

### 4.1 async 写操作无 guard 关键词（10 处）— 误报

扫描命中的 `runWrite` / `writeOnce` / `doImport` 等是底层函数（返回 Promise 给调用方），loading 由 UI 层负责：`DeviceBatchCommand.vue:138` 按钮有 `:loading="executing"`。`onDeleteSequence` 是同步本地删除 + `confirmDelete`。无一遗漏。

### 4.2 24 处重复 mock `@/utils/confirm` — 误报

逐条看内容：有的 mock `confirmDelete`、有的 mock `confirmAction`，有的用 `vi.fn()`、有的用 `vi.hoisted` 变量、有的直接内联——**变体各异，无法提取单一共享 helper**。

### 4.3 9 个组件 `defineProps` ≥8 字段 — 合理

绝大多数是 `industrial/` 下的表单控件（BusSelect / PresetNumberSelect / DurationSelect / BaudrateSelect），配置项多是控件天性；其余 LogPanel / InlineEditCell / Topbar 是多职责容器，无拆分必要。

### 4.4 composables 48% 同名 spec — 不是覆盖缺口

初次脚本用 import 路径匹配在 Windows 路径分隔符下失效，误报 80 个"无覆盖"（含明明有 spec 的 `useRequestGuard`）。改用同名匹配后为 40/82，但大量 composable 由宿主 view/组件 spec 间接覆盖（`useDevices` 子模块由 `useDevices.spec.ts` 覆盖）。全项目 261 spec / 2489 用例，规模健康。**不要用"同名 spec 比例"当作覆盖率指标。**

### 4.5 超时常量散落 — 低价值

`duration:8000` ×3、`Delay=3000` ×2 等，多为 Element Plus Toast 显示时长和局部重试间隔，语义清晰且集中在具体模块，集中到全局常量文件的收益极低。

## 5. 工具教训

1. **Windows 路径匹配**：`os.path.normpath` 保留反斜杠，与 spec 里 `@/` 别名拼接的路径格式不一致，导致"无测试覆盖"脚本误报 80 处。跨路径统计应统一用 `/` 或 `pathlib.as_posix()`。
2. **"扫描命中 ≠ 债"第三次应验**：本轮 10 个维度，9 个核实为健康/误报，只有 1 个（错误出口）成立。与 12/13/14 号教训一致——**不做清单和做清单同样重要**。
3. **注释也可能是线索而非结论**：`failureMessage` 注释说"写操作专用"，反而在读操作上发现了误用；反过来"错误出口已统一"的历史结论也不能照搬，必须回到当前代码核实。

## 7. 修复记录（P3 错误出口收敛 · 已落地）

用户拍板"修复一下"后执行。**核心原则：只改确凿走 `request` 且 method=GET 的读操作**；写操作（拦截器静音、页面 catch 是唯一出口）保持 `failureMessage` 不动；原生 `fetch`（不经过拦截器，不会重复弹窗）排除。

### 7.1 判定依据

`responseInterceptor.ts:33` 的 `isMutationRequest` = `method !== 'get'`：只有 GET 失败才会 `notify.error(...)` + `markUserNotified(error)`。逐处核对 API 定义确认 method：

- GET（改）：`listConfigVersions` / `getConfigVersion` / `exportConfig` / `listDevices` / `listPoints` / `getCellularStatus` / `getIoStatus` / `getAutoDetectResult` / `downloadArchive`
- 写操作（不动）：`backupConfig` / `rollbackConfigVersion` / `controlIo` / `upsertAssetView` / 各类删除保存
- 原生 fetch（排除）：`DeliveryCheck.fetchTemplate`
- 行内错误条（保留）：`LogArchive.vue:159` 的 `viewError.value`（服务于"空表≠无日志"语义，非弹窗）

### 7.2 逐文件改动

| 文件 | 改动 |
|---|---|
| `useConfigVersions.ts` | 3 处（加载版本列表 / 加载快照 / 对比版本）`failureMessage` → `showToast`；备份 / 回滚（写）保留 |
| `useConfigActions.ts` | 导出配置（GET）`extractErrorMessage` → `showToast`；其余写操作追加文案保留 |
| `useAutoDetect.ts` | 已引入的 `message` 换为 `showToast`；轮询进度（GET）+ 启动探测（POST）统一出口 |

### 7.5 关键教训

**错误出口迁移必须先按 HTTP method 分类，不能按"语义读/写"分**——`validateConfig` / `previewDiff` 语义是读但 method 是 POST，拦截器会静音、页面必须自己弹，误改会导致这些错误无人提示；`fetchTemplate` 走原生 fetch 不经过拦截器，也不存在重复弹窗。
