## 1. P0 — 阻断级（4 条）

### DD-01 · CJT188 帧布局前后端漂移，同一帧解析出完全不同字段
- **域**：D7 协议调试台 · **类别**：契约债
- **现象**：后端按 `68 + ADDR(7) + CTRL + LEN + DATA + CS + 16` 组织帧；前端假定帧内多 1 字节「仪表类型」，整体偏移 1 字节。
- **现场表现**：在协议调试台粘贴一帧真实 CJT188 报文，前端解析出的控制码/长度/数据全错位，与设备实际回帧对不上，现场按前端解析调设备必然调错。
- **证据**：
  - 后端：`gateway-core/src/south/protocol/common/frame_extract.rs:150`、`gateway-core/src/south/protocol/cjt188/frames.rs:71,82-89`（走 `build_68_frame(addr, false, false, ctrl, data, "CJT188")`，无第二个 0x68，地址 7 字节）
  - 前端：`gateway-web/src/utils/frameParser.ts:212-234`（`bytes[9]`=ctrl、`bytes[10]`=len、data 从 `bytes[11]` 起）
- **定级**：P0（前端离线解析器输出错误字段，是调试台的唯一离线依据）
- **建议动作**：以帧解析器单一真源为准 —— 要么前端改用后端同口径偏移（推荐，后端口径已带 CRC/长度自洽校验），要么前端解析结果标注「前端启发式解析，仅供参考」并把权威解析移到后端。
- **是否新增功能面**：否

### DD-02 · 寄存器扫描失败/中止后前端永不收尾
- **域**：D7 · **类别**：语义债
- **现象**：后端失败路径仍把 `progress` 置 100；前端只在 `status === 'done'` 时停止轮询。
- **现场表现**：扫描中途设备断线，页面永远转圈，运维以为还在跑，实际早已结束；对同一任务重复点扫描会堆积并发扫描。
- **证据**：
  - 后端：`gateway-core/src/protocol_tools/handlers/register_scan/scan.rs:106-110`
  - 前端：`gateway-web/src/composables/acquisition/useRegisterScan.ts:147`
  - 正确参照：`gateway-web/src/composables/acquisition/useAutoDetect.ts:54`（按 `status !== 'running'` 收尾）
- **定级**：P0（页面挂死，现场误判）
- **建议动作**：前端按 `status !== 'running'` 收尾，并区分 done/failed/aborted 三态展示；后端失败路径的 `progress` 不再置 100。
- **是否新增功能面**：否

### DD-03 · 回放中止/失败被静默掩盖为「完成」
- **域**：D7 · **类别**：语义债
- **现象**：后端遇 Aborted/Failed 后 break，仍返回 200 + 部分汇总；前端无 `onAborted` 回调，用 `summarizeFrames()` 在本地重建一份「完成」汇总。
- **现场表现**：回放会话在第 3 帧就中止，页面显示「回放完成，N 帧全部一致」——现场据此判定「协议 OK」，而真实情况是链路已断。这是**把失败报成成功**，比缺失数据更危险。
- **证据**：
  - 后端：`gateway-core/src/protocol_tools/handlers/packet_replay/replay_run.rs:153-177`
  - 前端：`gateway-web/src/composables/acquisition/usePacketReplay.ts:198-203`
- **定级**：P0（失败被报成成功）
- **建议动作**：后端中止时返回非 200 或在响应体带明确终态字段；前端不得本地重建汇总，必须以后端终态为准，并在中止时显式提示。
- **是否新增功能面**：否

### DD-04 · chaos 集成测试 5 例失败，重作业/发布门禁当前为红
- **域**：跨域（门禁） · **类别**：测试债
- **现象**：`cargo test --workspace` 实测 `gateway-core --test chaos`：**40 passed / 5 failed**。三类根因：
  1. **测试桩回帧 unit_id 写错**（3 例）：`harness.rs:275` 把 `pdu.first()`（= 功能码）当作 unit_id 回填，而请求的 unit_id 在 `header[6]`。客户端期望 unit_id=1，实收 3 → `unit_id mismatch: expected 1, got 3`。该桩在 `ab44c3d`（2026-11-20）为响应增加 unit_id 校验后即失效，此前被掩盖。
  2. **断言陈旧 - BACnet**（1 例）：`ae827f2` 把 WriteProperty 的 Abort/Error/Reject 明确归为「确定未生效 → 可安全重试」，实现改为 `DeviceRejected`；场景仍断言旧的 `InvalidFrame`。
  3. **断言陈旧 - 串口写**（1 例）：`ae827f2` 统一写语义后，「已下发无应答」由 `NoReply` 改判 `WriteUncertain`；场景仍断言 `NoReply`。
- **现场表现**：`.github/workflows/heavy.yml` 的 `chaos` 作业失败；`release-gate.yml` 无条件调用 heavy.yml → **打 tag / 手动触发 / 每周定时发布门禁全部失败**，发布事实上被阻断。CI 里长期挂着的红作业会掩盖后续真实失败。
- **证据**：
  - 桩：`gateway-core/tests/chaos/harness.rs:275`（`out.push(pdu.first().copied().unwrap_or(0))`）；请求侧 unit_id 在 `header[6]`
  - 校验：`gateway-core/src/south/protocol/modbus/transaction/frame.rs:85,122` → `transaction.rs:396-411`（`deliver` 的 unit_id 比对）
  - 场景断言：`gateway-core/tests/chaos/scenarios.rs:512,640,3207`（unit_id）、`:2694`（BACnet）、`:2622`（串口写）
  - 生产实现：`gateway-core/src/south/protocol/bacnet/frames/write.rs:139-143`（`DeviceRejected`）、`gateway-core/src/south/protocol/modbus/trait_impl.rs:28-29`（`mark_write_uncertain`）
- **定级**：P0（发布门禁红）
- **建议动作**：
  1. 桩回填 unit_id 改为 `header[6]`（回显请求的从站地址），这是协议正确行为；
  2. 两处断言对齐新语义（BACnet 改判 `DeviceRejected`、串口写改判 `WriteUncertain`），并在断言旁注明语义变更来源（`ae827f2`）；
  3. 属**测试代码与注释**修订，不改生产逻辑。
- **是否新增功能面**：否

## 2. P1 — 必修级（36 条）

### 2.1 架构债与门禁债

#### DD-05 · `await_holding_lock` 违规，且本仓编译通过依赖第三方 crate 传递开启 `parking_lot/send_guard`
- **域**：跨域 · **类别**：架构债 + 门禁债
- **现象**：`runtime/gateway.rs:635-636` 在 `if let Some(old) = self.bus_managers.lock().get(&name).cloned()` 的临时 guard 借用期内 `.await`。
- **现场表现**：**本仓能编译，是因为 `parking_lot` 的 `send_guard` feature 被 `async-opcua-client/core/server v0.19.0` 传递性开启**（`cargo tree -e features -i parking_lot --workspace` 实证），使 `MutexGuard` 变 `Send`。一旦 opcua 依赖树变化或升级，`future cannot be sent between threads safely` 会直接编译失败——**编译通过与否取决于第三方传递依赖的 feature 开关**，这是隐性架构债。
- **证据**：
  - `gateway-core/src/runtime/gateway.rs:632-637`（`if let Some(old) = self.bus_managers.lock().get(&name).cloned() { old.close_task(...).await; }`）
  - 锁序文档已明文禁止该写法：`gateway-core/src/south/scheduler/mod.rs:21-48` LOCK ORDER 表
  - 实证：独立探针（未启用 `send_guard`）rustc 报 `future cannot be sent between threads safely ... MutexGuard ... which is not Send`
- **定级**：P1
- **建议动作**：按 LOCK ORDER 表自身的指引改写 —— 先 `let old = { let g = self.bus_managers.lock(); g.get(&name).cloned() };`（guard 在 await 前已释放）再 `old.close_task(...).await`；或改 `tokio::sync::Mutex` 显式 await。
  **注意精确表述**：`.cloned()` 之后 guard 已不再被借用，await 时**并不实际持锁**；clippy 报的是借用期跨越 await。
- **是否新增功能面**：否

#### DD-06 · `PointConfig.timeout_ms` 后端 `Option` ↔ 前端必填，契约漂移
- **域**：跨域（前后端契约） · **类别**：契约债
- **现象**：后端 `pub timeout_ms: Option<u64>` + `#[serde(default)]` + `#[ts(type = "number")]` → ts-rs 生成**必填** `timeout_ms: number`；而同一文件的 `write_min`/`write_max` 用 `#[ts(optional)]` → 生成 `write_min?: number`。ts-rs 对 `Option` 的映射口径未统一。
- **现场表现**：`npm run type-check` 失败 4 处（TS2322 ×3 + TS2741 ×1）：`usePoints.spec.ts:83`、`pointDefaults.ts:34`、`PointsBatchEditDialog.spec.ts:44`、`PointsCopyDialog.spec.ts:35`。**已跑 `npm run types:export` 后错误依旧** → 不是绑定未重生成，是真实的契约漂移。
- **证据**：
  - `gateway-core/src/config/point.rs:132-139`（timeout_ms）、`:197-208`（write_min/write_max 用 `#[ts(optional)]`）
  - `gateway-web/src/api/generated/PointConfig.ts:77`（`timeout_ms: number,` 必填）、`:137,143`（`write_min?: number,`）
  - `gateway-web/src/utils/pointDefaults.ts:33-34`（`defaultPointConfig()` 不含 timeout_ms）
- **定级**：P1
- **建议动作**：统一 `Option` 的 ts-rs 口径 —— 对确实可空的字段统一用 `#[ts(optional)]`（并同步生成的 `PointConfig.ts`），或改 `#[ts(type = "number | null")]` 后同步前端 4 处。**二选一，不并存**。
- **是否新增功能面**：否

#### DD-62 · 诊断日志 WebSocket 缺少实时流已具备的三层防护
- **域**：D10 · **类别**：架构债
- **现象**：实时数据 WS（`realtime`）已具备 4 层防护 —— ①连接数上限（`WsSlot::try_acquire`，超限 503）②单连接发送缓冲上限（`WS_OUT_BUFFER=32`）③单条发送超时（`WS_SEND_TIMEOUT=5s`）④读写分离（writer 独占 sink）。**诊断日志 WS（`diagnostics_logs_ws`）三层全无**：无连接数上限、无有界缓冲、`socket.send()` 无超时，且读循环直接 `socket.send().await`（慢客户端会阻塞整个订阅循环）。
- **现场表现**：多个浏览器页签开着「实时日志」且其中一个网络慢 → 该连接拖住日志广播消费，其它客户端日志卡顿；同时日志 WS 可被反复重连无上限占用。日志流本身走 `broadcast`（`Lagged` 时 `continue` 静默跳过，见 `:87`）→ 丢日志无提示。
- **证据**：
  - 有防护的一侧：`gateway-api/src/web/api/realtime/handlers/mod.rs:237-277`（`WsSlot` / `WS_OUT_BUFFER` / `WS_SEND_TIMEOUT`）、`:14`（`WS_OUT_BUFFER`）、`:16-18`（`WS_SEND_TIMEOUT`）
  - 缺防护的一侧：`gateway-api/src/web/api/realtime/handlers/mod.rs:69-115`（`diagnostics_logs_ws` 全段）
  - 连接上限实现：`gateway-api/src/web/api/realtime/handlers/limit.rs:16-31`
- **定级**：P1
- **建议动作**：把实时 WS 已验证的四层防护同样接到日志 WS（连接数可与实时流分开计数）；`broadcast` 的 `Lagged` 分支应计数并提示，而非静默 `continue`。
- **是否新增功能面**：否

#### DD-63 · 死信重投/清理端点落到**可授予**的 `config:write`，与路由注释「必须强鉴权」矛盾
- **域**：D10 · **类别**：架构债（权限层级）
- **现象**：死信运维端点位于 `/api/north` 前缀下（`system/routes.rs:61,91,94`），而 `required_write_scope` 把 `/api/north` 整段映射为 `config:write`（`middleware/auth.rs:298-309`）。**`config:write` 在可授予白名单 `ALL_SCOPES` 内**（`access/handlers.rs:196-204`），而系统域用的 `system:write` 明确**不在**白名单（注释 `auth.rs:266-268`：「系统域写操作只有主 token 能通过，避免 API 密钥通过建用户/建密钥提权」）。路由注释 `system/routes.rs:89` 写的是「重投与清理都必须强鉴权」。
- **现场表现**：一个仅被授予 `config:write` 的 API 密钥，即可**重投（重新对外发包）和销毁（清除唯一副本）北向死信**——死信里含失败报文原文与可能的凭据（`auth.rs:411` 已把它列为敏感读路径）。权限层级比注释承诺的弱一档，且与 `system:write` 的设计意图不一致。
  （读端点 `GET /api/north/dead-letters` 已列入 `is_sensitive_read_path`（`auth.rs:424-425`），即使开启匿名读也强制鉴权 —— **读侧无缺口，缺口在写侧**。）
- **证据**：
  - 端点定义与注释：`gateway-api/src/web/api/system/routes.rs:61,89-94`
  - scope 映射：`gateway-api/src/web/middleware/auth.rs:298-309`（`/api/north` → `config:write`）
  - 可授予白名单：`gateway-api/src/web/api/access/handlers.rs:196-204`（含 `config:write`，不含 `system:write`）
  - 设计意图注释：`gateway-api/src/web/middleware/auth.rs:266-268`
  - 敏感读路径（读侧已覆盖）：`gateway-api/src/web/middleware/auth.rs:411,424-425`
- **定级**：P1
- **建议动作**：把死信**写**端点从 `/api/north` 前缀映射中单独剥离，归入不可授予的 `system:write`（与 `/api/system`、`/api/watchdog` 同级）；保留普通北向配置写仍为 `config:write`。**属权限分层修正，不新增端点**。
- **是否新增功能面**：否
