必须先剔除**动态 `import()`**：项目已用 **130 处动态 import** 刻意断环（`responseInterceptor.ts:186` 跳登录、`stores/auth.ts:127` 拉 license、`useSessions.ts:126` 跳登录等，注释均写明理由）。把这些算作依赖会产出 68 组假环。**剥离 barrel 与动态 import 后，真正剩下的静态环是 5 组**：

```
api/index.ts ⟶ api/http/index.ts ⟶ api/http/responseInterceptor.ts ⟶ stores/auth.ts ⟶ api/index.ts
api/index.ts ⟶ api/http/index.ts ⟶ api/http/responseInterceptor.ts ⟶ stores/auth.ts ⟶ api/auth.ts ⟶ api/index.ts

stores/auth.ts ⟶ composables/system/useSessions.ts ⟶ stores/auth.ts          ← 最短环，只剩 2 个节点
api/http/index.ts ⟶ api/http/responseInterceptor.ts ⟶ stores/auth.ts ⟶ api/http/index.ts
```

**根因只有一个**：`api/http/responseInterceptor.ts:12-14` **静态**引入了三个 store：

| 位置 | 导入 | 后果 |
|---|---|---|
| `src/api/http/responseInterceptor.ts:12` | `useNotificationsStore` from `../../stores/notifications` | 传输层 → 状态层 |
| `src/api/http/responseInterceptor.ts:13` | `useRequestLogStore` from `../../stores/requestLog` | 同上 |
| `src/api/http/responseInterceptor.ts:14` | `useAuthStore` from `../../stores/auth` | 同上，且 `stores/auth.ts:3` 又 `from '@/api'` → 回指 api barrel |

**对照证据：同一个文件里已经用对了做法**——`responseInterceptor.ts:186` 跳登录用 `void import('../../router')`，`stores/auth.ts:127` 拉 license 用 `void import('./tier')`，两处都带注释说明是为断环。**唯独第 12-14 行的三个 store 是静态导入**，这正是 5 组静态环的唯一源头。

**环枢纽排行**：`stores/auth.ts` 出现在 5/5 组，`api/http/index.ts` 4/5，`responseInterceptor.ts` 4/5。

**修法**：把 `responseInterceptor.ts:12-14` 的三个 store 改为动态 import（与同文件 186 行同款），或把"写请求日志 / 弹通知 / 401 登出"下沉到 `api/http/` 自身的模块级回调注册表，由 `app/main.ts` 注入 store。前者改动小、后者更干净。

### A-2 【P1】`stores/auth.ts` ⟷ `composables/system/useSessions.ts` 2 元环 —— **已修（DD-66）：会话上移为 store，静态环归零**

**原始形态**（修前）：

```
stores/auth.ts:5        import { useSessions } from '../composables/system/useSessions'
composables/system/useSessions.ts:9    import { useAuthStore } from '@/stores/auth'
```

- `stores/auth.ts:119` 在 `login()` 里调 `useSessions().markLogin()`；
- `useSessions.ts:120` 在强制下线里 `useAuthStore().$patch({ loggedIn: false, token: '' })`。

**语义问题不止于环**：按 `src/composables/README.md:114-126`（自称"Store vs Composable 边界（唯一真源）"），登录会话是**跨页面共享、需长期驻留**的数据（`useSessions.ts:3` 自述"前端模拟登录会话"，消费方含 `stores/auth.ts`、`composables/system/useSystem.ts:70`、`views/system/overview/SystemOverview.vue:269`），判定归属应当是 **store**，不是 composable。现在的形态是"store 反向依赖 composable"，方向与该文档的判定表相反。

> 注意：`frontend-state.md:62` 把 `useSessions` 登记进 `@singleton` 表，说明现状是**被登记过的已知形态**，只是登记的归属结论与 `composables/README.md` 不一致（见 D-6）。

**修法（2026-11-28 落地，用户 2026-11-28 拍板「上移为 store」）**：

| 环节 | 做法 |
|---|---|
| 归属上移 | `composables/system/useSessions.ts` → **`src/stores/sessions.ts`**（Pinia store `useSessionsStore`），`LoginSession` 类型一并迁到 `stores/sessions.ts:26` |
| 断 `auth → sessions` | `stores/auth.ts` 不再引会话模块；`login()` 里的 `useSessions().markLogin()` 移出，改由**调用方** `views/auth/Login.vue:292` 在登录成功后显式调 `useSessionsStore().markLogin()` |
