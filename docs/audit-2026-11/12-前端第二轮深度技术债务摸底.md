## 2. 按功能域的新发现

### 2.1 SystemHub 系统设置 / Auth 登录 —— 架构债（P3，观察项）

**一段真实静态小环**：`stores/auth.ts:6 → api/http/index.ts:26 → responseInterceptor.ts:14 → stores/auth.ts`，外加 `stores/auth.ts:5 ↔ useSessions.ts:9`。这是全项目唯一"模块顶层值互相引用"潜力的地方。

- **为什么现在没事**：`stores/auth.ts:19` 的 `defineStore('auth', () => {...})` 是工厂函数、`responseInterceptor.ts:37` 起是回调，顶层只做函数绑定，模块初始化阶段不读未就绪的值。
- **风险边界**：将来若有人在模块顶层直接读 `useAuthStore()` 的字段，这里就会变成真 TDZ。
- **建议**：把 `stores/auth.ts:6` 的 `markLoggingOut/resetLoggingOut` 从 `@/api/http` barrel 改为直接 `import from '@/api/http/loggingOut'`，绕开 `index → responseInterceptor` 回边；**无需动** useSessions 的动态 router import。

**27 文件大环不是债**（澄清，避免过度报告）：典型闭合路径 `router/index.ts:3 → routes/index.ts:164 → SystemHub.vue:37 → HubShell.vue:111 → stores/auth.ts:5 → useSessions.ts:126 →（动态）router/index.ts`。其中 `routes → view` 是 `() => import(...)` 懒加载、`useSessions → router` 是函数体内 `void import('@/router')`——都在延迟阶段执行，模块加载顺序安全。**要守的底线**：这两条动态 import 不得改成顶层静态 import。建议把这行底线写进 `docs/architecture/frontend.md`，防后人"好心"重构。

**缺失的门禁**：`eslint.config.js` 无 `import/no-cycle`，项目未装 `eslint-plugin-import` / `madge`，CI 也无环检测。目前环的规避全靠开发者注释约定（如 `api/inflight.ts:4-8`、`router/index.ts:102`）。若要上门禁，先用能忽略注释文本、把 `export … from` 当单向边的工具（如 madge 配 `tsconfig`），否则会报出 3 组假环。

### 2.2 ConfigHub 配置管理 —— 结构债（P3，确认死代码）

**`src/stores/config.ts` 是零引用死 store**。

- `useConfigStore`（`:16`）全仓库零引用（含 spec / e2e / scripts，排除 node_modules），无 `stores/index.ts` barrel 间接路径。
- 文件本身实现完整（load/save/reload/invalidate，`:26-92`），但功能已被 `composables/config/useConfigActions.ts:1-40` + `useConfigJson.ts` + `useConfigVersions.ts` 完整替代，实际挂载点是 `views/system/config/RuntimeConfig.vue:213,242`。
- **建议**：删除该文件（或加废弃注释）。**风险**：维护者误以为配置走这个 store，改了它却不生效——这是留着它的唯一实际危害。

### 2.3 全站工具层 —— ❌ 初版误判，已撤销（见 §7）

初版把 `src/utils/ep-icons-compact.ts` 判为"被替代的旧图标方案、建议连 spec 删除"。**这是错误结论**：该文件是 `vite.config.ts:74` / `vitest.config.ts:26` 的 alias 目标，全站所有 `@element-plus/icons-vue` import 都被重定向到它。修复阶段实测删除后 **所有测试与 dev 构建崩溃**（`Failed to resolve import "@element-plus/icons-vue" from src/test/setup.ts`），已完整恢复。**不要删除**。

### 2.4 数据流水 / 运维监控 —— 语义债（P3，需产品确认）

### 2.5 全站契约层 —— 架构债（P3，需人工确认）

**14 个 ts-rs generated 类型未被前端直接 import，前端另有手写同名接口**。

- `api/generated/` 下 `CertificateInfo.ts` / `TopologyData.ts` / `PointQuality.ts` 等 14 个文件未被 `generated/index.ts` 导出，全项目出现的同名类型来自手写接口：`dataQuality.ts:26,37,55`、`topology.ts:12-38`、`remoteControl.ts:13,21`、`watchdog.ts:14,34`、`webhook.ts:16`、`protocolTools/types.ts:103`。
- **文件不可删**：文件头标 `generated by ts-rs. Do not edit`，`package.json` 的 `types:export` / `types:check` 依赖整个目录，删除会破坏 git diff 校验。
- **风险**：后端 ts-rs 契约变更后，前端手写接口不会自动跟随，存在字段漂移。**需人工确认**：是否让前端直接复用 generated 类型以消除双份维护？这是跨端契约治理话题，超出"前端补丁"范围，建议纳入 next roadmap。

### 8.2 generated 契约直用（原 §2.5）—— 字段名真源归 generated

**关键约束**：generated 目录由 ts-rs 生成、受 `types:check` 的 `git diff` 门禁保护，**全程未修改任何 generated 文件**；字段名以契约为真源，只覆盖视图差异（bigint→number、字面量收窄、可空→可选），运行时行为不变。此范式项目里 `watchdog` / `protocolTools` 早已验证。

**改动 7 处手写接口改为从 generated 派生**（`Omit<Raw,差异字段> & 视图差异`）：

| 文件 | 类型 | 覆盖的视图差异 |
|---|---|---|
| `api/dataQuality.ts` | `PointQuality` / `PointBackoff` | bigint 时间戳→number、quality 收窄字面量 |
| `api/dataQuality.ts` | `QualityStats` | 完全一致，直接复用契约类型 |
| `api/topology.ts` | `TopoNode` / `TopologyData` | node_type 收窄字面量（nodes 指向收窄后的节点） |
| `api/topology.ts` | `TopoLink` / `TopoStats` | 完全一致，直接复用契约类型 |
| `api/remoteControl.ts` | `WritablePoint` / `ControlCommand` | status 收窄、bigint 时间戳→number |
| `api/watchdog.ts` | `HealEvent` / `HealAction` / `ServiceStatus` | bigint→number、detail 可空→可选；两个枚举直接 re-export 契约 |
| `api/webhook.ts` | `WebhookTestResponse` | bigint latency→number、可空 error→可选 |
| `api/certificates.ts` | `Certificate`（保留导出名） | bigint 时间戳→number、bound_to 可空→可选 |

**收益**：后端 ts-rs 契约一旦加/删/改字段，前端视图自动继承或在 type-check 立即暴露，消除"后端改契约、前端手写接口静默漂移"的风险。

**守护测试**：新增 `api/generatedContract.spec.ts`——编译期用 `IsEqual<keyof 视图, keyof 契约>` 断言 6 组视图字段集与契约严格一致，运行时用字段名快照锁定，漂移时给出明确失败点。
