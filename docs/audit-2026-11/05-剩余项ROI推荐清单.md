> **这份清单是什么**：把所有还没做的待办合并成一张表，统一排优先级。三类来源：
> ① **改代码的**——[04-ROI推荐清单.md](04-ROI推荐清单.md) 前 7 批做完后剩下的 8 项（含旧清单遗留）；

> ③ **门禁的**——`security` workflow 里 cargo-audit 的依赖告警（SEC-01，2026-11-23 新增）。
> **范围**：只修现有的东西，不做新功能（双机热备 / 云平台 / 数据分析平台仍冻结）。
> **怎么读评分**：
> - **工作量**：S = 半天以内，M = 1~3 天，L = 4~7 天，XL = 超过一周；
> - **价值**：高 = 涉及安全或数据错误、或挡着别的活；中高 = 正确性防线；中 = 好排查、好用；低 = 记录用；
> - **ROI 档**：A = 划算，马上做；B = 本季做；C = 有空再做；D = 先放着，等外部条件；
> - 标「→ 同源」的条目要么改的是同一处代码、要么需要同一次决策，**一起做，工作量不重复算**。

## 1. ROI-35 所有写操作走同一条路（DD-33 / DD-34 / DD-35 / DD-36 / DD-56 · P1）

- **现在的毛病**：写点位本来有一条统一入口——范围检查、写完再读一遍确认、记审计，都在这一步做。但 **OPC UA 的写绕开了它**：自己写、自己报错，把「成功 / 失败 / 结果未知」三种结局压成了一种。还有三处：
  - 写不存在的点、写不能写的点、写超范围的值——**审计和计数都是空白**（成功的反而有记录）；
  - 写超时时，审计记的格式和控制历史认的格式对不上，解析失败还按 0 处理 → **「结果未知」的写，在控制历史里显示成「成功、写了 0」**；
  - 审计里的「操作人」永远是 `api` / `opcua`，「设备名称」列填的是设备 ID；网页远程控制的操作人输入框**从来没上报过**。
- **现场会看到什么**：同一个写动作，走不同入口结果不一样（一个能写超范围、一个把可疑结果报成成功）。查「谁在什么时候写过这个点」只能看到一片 `api`，误操作和越权都没有依据。
- **工作量**：**L（约 1 周）**。把 OPC UA 的写并回统一入口，统一审计格式和操作人来源，补上写失败的审计。
- **价值**：**高**。修的是「结果未知被显示成成功」和「写失败不留痕」两类高危问题，也是写语义这条线的收尾。
- **依赖**：不用等任何决策，可马上开工。「增量 / 脉冲」点位的读回规则留给 ROI-15。
- **对应债务**：DD-33、DD-34、DD-35、DD-36、DD-56
- **建议**：**下一批就做这个**。问题位置已勘察清楚，属于「已定位缺陷」。

## 2. DD-14 质量规则改为运行时装配持有（独立待办 · P1）

- **现在的毛病**：「质量规则」装在一个**进程级全局变量**里，而且是由网页层绕路塞进去的（正式启动路径不走这里），塞失败只留一条日志。配置写接口返回 200 就算成功（这一点已在第 4 批修掉）。
- **现场会看到什么**：配置保存成功、界面看着正常，**规则实际没生效**。
- **工作量**：**M（约 3~5 天）**。规则表改成由运行时持有，网页层只调现成的接口。
- **价值**：**中高**。属于「配置和实际行为脱节」——一旦踩中，全线数据都不对。
- **依赖**：要确认启动路径和网页层各管什么。
- **对应债务**：DD-14（已定为独立待办，不并入其它批次）
- **建议**：ROI-35 之后单独一批做。

## 3. ROI-44 调试台的资源边界与安全边界（DD-25 ~ DD-32、DD-47 ~ DD-49 · P1/P2）

- **现在的毛病**：调试台一共 11 条债，归成 4 类：
  1. **队列不限长（无背压）**：事件流来多少存多少，前端处理不过来就直接丢；
  2. **没有隔离**：回放会话全局存一份、永不过期——局域网里任何登录用户都能看到、删掉别人的会话，还会越堆越多；
  3. **暴露面太大**：从站模拟默认监听**所有网卡**（不只本机），全局还只能起一个；
  4. **一件事两个答案**：报文解析只有 Modbus 由后端做、其余协议前端自己解；「异常帧算不算在线」两处判定正好相反；编辑报文发写帧**没有二次确认**（同页的调试向导却有）。
- **现场会看到什么**：多人共用一台网关调试时互相干扰；开着从站模拟等于**对整个局域网开放一个从站**；误填一帧写命令直接下发到生产总线。
- **工作量**：**L**。背压和会话隔离是结构性改动，其余多为局部修正。约 3~5 天起。
- **价值**：**中高**。多数不直接影响数据正确性，但「局域网暴露」「写帧无确认」两条有安全含义。
- **依赖**：**可拆两批**——先「队列上限 + 会话归属 / 过期」（DD-26/27/28/29），再「暴露面 + 双口径 + 二次确认」（DD-25/30/31/32/47/48/49）。
- **对应债务**：DD-25 ~ DD-32、DD-47、DD-48、DD-49

## 4. ROI-43 固件升级要验签，验不过就别装（DD-40 / DD-46 · P1）

- **现在的毛病**：固件包**只校验 CRC32，不验签**，而且校验不过也照样装；上传接口一律回 200「上传中」，审计记录写在处理之前、没有结果。
- **现场会看到什么**：改过的固件包能装进现场网关（CRC32 很容易伪造），装不上也不会被拦住；审计里只有「开始升级」，看不出成没成功。
- **工作量**：**L（约 1 周）**。接入签名校验（仓库里授权模块已有同类机制可复用）+ 校验失败一律拒绝 + 审计补结果。
- **价值**：**高**。安全防线，一次投入长期受益。
- **依赖**：**先定签名方案**（复用现有签发体系还是新增）——这是产品决策项，**不自行编造密钥 / 方案**。
- **对应债务**：DD-40、DD-46

## 5. ROI-09 批量写要说明白「能不能整批重试」（W-2 · P1）

- **现在的毛病**：一次写多个点时，成功和失败混在同一个返回数组里，接口**没说清**这批是「全成功才算数」还是「可以整批重试」。
- **现场会看到什么**：上游看到 200 但部分失败，就整批重试 → **已经成功的点被写了第二次**。对累加型、脉冲型点位就是重复动作。
- **工作量**：**M（约 3~5 天）**。接口说清语义 + 批量写加幂等键（同一个请求重复发，效果和发一次相同）+ 文档说明。
- **价值**：**中**。防重复动作；要和上游一起改接口，协调成本比改代码高。
- **依赖**：**需与上游约定**；**建议并入 ROI-35**（批量写语义要在统一入口上声明，否则改两遍）。
- **对应债务**：W-2（与 DD-33/34 同一片代码）

## 6. ROI-15 写属性建模：区分「设定值 / 增量 / 脉冲」（W-3 / G-04 · P1/P2）

- **现在的毛病**：点位没法声明「这个点写进去是设定值、增量、还是脉冲」，写完读回核对只认设定值这一种。
- **现场会看到什么**：增量型点位被上层用「多次写」模拟时，读回比对必然对不上 → 每次都得人工核实。
- **工作量**：**L（约 1 周）**。改点位模型 + 各协议写路径 + 读回比对逻辑。
- **价值**：**中**。前提是现场真用增量 / 脉冲点位，用得少就不划算。
- **依赖**：**先确认现场有没有这类点位**；**排在 ROI-35 之后**（先统一入口，再在其上声明语义）。与 G-T0 的 W-09/G-04 是同一个决定。
- **对应债务**：W-3、G-04

## 7. ROI-14 让 Modbus 的多个从站组同时干活（S2 · P1/P2）

- **现在的毛病**：Modbus 读路径按（从站，功能码）分组，**组内已经并发**，但**组与组之间是一个一个串行跑的**。
- **现场会看到什么**：从站多的现场（比如一条总线上 30 台设备），采集一轮要等很久才轮完。
- **工作量**：**L（约 1 周）**。组间并发，同时保证同一条 RS485 总线上时序不乱（同一时刻只能有一个从站应答）。
- **价值**：**中**。**强依赖现场从站数**——从站少就没收益。与 G-T0 的 TCP-09/G-05（一台设备不应答能否卡死整条总线）是同一个决定。
- **依赖**：先确认现场典型从站数；排在 ROI-45（锁序，已完成）之后，避免踩锁序问题。
- **对应债务**：S2

## 8. ROI-13 改了配置文件就自动生效，不用重启（C-2 · P2）

- **现在的毛病**：只有「网页上保存配置」才会重新加载。直接改磁盘上的 `config.json`，**重启之前完全没效果**。
- **现场会看到什么**：改完没用，以为写错了反复改；或者干脆改完重启，撞上热重载的半生效窗口。
- **工作量**：**XL（约 1~2 周）**。加文件监听 + 处理「文件写到一半被监听到」的坑 + 平台差异（Windows / Linux / 嵌入式）。
- **价值**：**中**。属于体验优化，不是修故障。嵌入式上文件监听还有功耗和可靠性代价。
- **依赖**：ROI-12（热重载原子性，已完成）已铺路；**放最后**——改动面最大、收益最看现场习惯。
- **对应债务**：C-2

## 9. SEC-01 依赖安全告警让 security 一直红（2026-11-23 新增 · S-M · 中高 · A）

- **现在的毛病**：`security` workflow 的 cargo-audit 报三条依赖公告：
  - `cookie` < 0.18.3 —— 进程 fork 后私有 cookie 的 nonce 可能重复；
  - `url` < 2.5.9 —— 嵌套 `blob:` URL 调 `origin()` 会栈溢出（拒绝服务）；
  - `heapless` < 0.9.4 —— 9 条公告（`IndexMap` 不变量、`Deque` 边界、Treiber 栈竞态、`zeroize` 等）。
- **现场会看到什么**：功能上不受影响，但**安全门禁长期红着**——真出问题时没人会再信这个红灯；对外也拿不到「安全扫描通过」的结论。
- **工作量**：**S-M（半天~2 天）**。`cookie` / `url` 一般 `cargo update -p` 即可；`heapless` 若被旧版协议依赖钉住，要连同上游包一起升。
- **价值**：**中高**。三条在本项目基本不可利用（网关不 fork、`blob:` URL 不由网关解析），但**红着的门禁等于没有门禁**。
- **依赖**：无。
- **建议**：作为 W0 之前的热身，半天级，先让 `ci` + `security` 两条 workflow 都绿。
- **状态**：✅ 2026-11-26 已处理。`url` → 2.5.9、`cookie` → 0.18.3（根锁与 fuzz 锁同步；`form_urlencoded` 随 url 升到 1.2.3）。`heapless` 无法升级：`async-opcua` 0.19.0（最新）→ `postcard` 1.1.3（最新）仍要求 `^0.7`，9 条公告按既有「上游无修复版本」口径豁免并登记 NB-06，等上游升级后删除。

**登记模板**（复制即用）：

```markdown
| NB-xx | 第 N 批 | path:line | 一句话 | 补断言/新增用例/需产品口径/需改实现 | 小/中/大 | 低/中/高 | 待处理 |
```

**四种类型怎么选**：
- **补断言** —— 代码是对的，只差测试；
- **新增用例** —— 完全没有测试，要新写；
- **需产品口径** —— 行为该怎么定还没结论，先定规则再动手；
- **需改实现** —— 确认是缺陷，要改代码（同时去 [02-技术债务清单.md](02-技术债务清单.md) 立 DD 编号）。

## 12. 补测试 9 批详情

> 每条缺口的实现位置和现有测试证据见 [08-守护缺口总表.md](08-守护缺口总表.md) 与 `07-guard-check/` 四份分册，这里只放排期要用的信息。

### G-T0 · 先定规则（16 条 · M · 高 · A）

- **是什么**：16 条「清单说的和代码做的不一致」或「功能根本不存在」。**规则没定就写测试，等于把可能错的行为固定下来**，所以先出结论、后写测试。
- **16 条是**：I-40（`persist_failed` 到底算什么）、B-12（串口在途不许打断是物理约束还是缺陷）、W-09/G-04（点位「设定值 / 增量 / 脉冲」要不要建模，→ ROI-15 同一个决定）、TCP-09/G-05（一台设备不应答能否卡死整条总线）、MC-W3、FINS-R8、FINS-W4、FINS-E1、FINS-E2、S7-R9、MSTP-R6、MSTP-R8、U-4、U-7。
- **为什么值**：多数条目定完规则只需 1~2 个测试；不定义就永远悬空，还会持续误导读清单的人。
- **验收**：一份决议表，每条三选一（按现状保留 / 改实现 / 不建模）+ 理由。

### G-T1a · 写路径 8 条规则补测试（S-M · 高 · A）

- **8 条是**：B-02（读重发次数）、B-03（写事务按「不重试」算预算）、RTU-12（写路径 0 重试预算）、RTU-07（3.5 字符帧间隔）、RTU-08（RS485 发送使能建立时间）、RTU-09（读前使能保持时长）、**TCP-04（两个写不许同时下发——代码里有信号量保证，全仓却没有一个测试，改坏了不会报警）**、TCP-08（写和读共用一个连接的并发上限）。
- **依赖**：与 ROI-35 同一处代码，**必须合批**。

### G-T1b · 写后不读回 / 不重试（5 条 · S · 中高 · A）

- **5 条是**：MC-W4、FINS-W5、S7-W5（协议层写完不自己读回——读回只在接口层拿不准时做一次）、MC-W5、FINS-W3（写失败不自动重发）。
- **为什么值**：把现有的正确行为锁住，防止以后有人顺手加重试，把「不能重复执行」的写变成重复动作。
- **依赖**：与 ROI-35 / G-T1a 同批。

### G-T1c · 数据处理 8 条（M · 高 · A）

- **8 条是**：I-12（公式算错时退回简单换算 `scale*raw+offset`，零测试）、I-15（`scale=0` 时不反推）、I-21（NaN/Inf 直接放行且不更新基线）、I-23（空窗口占位的质量标 `Bad`）、I-30（错误点数值为 0）、I-32（虚拟点沿用源时间戳）、**I-34（停用的虚拟点不参与计算、不出数，15 个虚拟点用例没有一个测过「停用」）**、I-52（处理阶段顺序）。
- **为什么值**：这些决定「报给上位机的数对不对」，其中 I-12 / I-34 完全没有测试。

### G-T1d · 热重载时在途写怎么收场（4 条 · M · 中高 · B）

- **4 条是**：U-2（写一半被取消，必须报「结果未知」而不是「连接已关」）、U-3（热重载和在途写同时发生：旧事务什么结局、旧连接活多久、会不会对同一设备重复下发）、U-5（先关旧串口再开新口的顺序）、U-6（重开串口失败要能自动恢复并报错）。
- **依赖**：先等 G-T0 定了 U-4（跨代写）的规则，测试才能定方向。

### G-T2a · 协议族边界 15 条（M · 中 · B）

- **15 条是**：MC-R1/R4/R6/R10/R11、FINS-R2/R5、S7-R2（**TPKT 报文没有总长上限**）、IEC-R4/R5、MSTP-R1/R4、UA-R2/R5/R6。
- **做法**：按协议族拆开，每族 2~4 条，改哪族补哪族。
- **状态**：✅ 2026-11-26 已补 15 条（测试位置见 08 的 4.1）。唯一未闭合的是 S7-R2 的 TPKT 总长上限：代码与文档都没给数值，需产品定口径（NB-07）。

### G-T2b · 数据链路与总线边界 21 条（L · 中 · C）

- **21 条是**：RTU-02、W-11、I-02/I-04/I-05/I-18/I-19/I-20/I-33/I-37/I-38/I-42/I-43/I-44/I-45/I-51/I-56、B-11、B-14、R-03、TCP-07。
- **为什么档低**：条数多但单条价值有限，适合一批一批补。

### G-T3 · 观测与一致性 16 条（S-M · 中 · C）

- **16 条是**：I-46/I-47/I-48/I-49、MC-R7/MC-E2、FINS-R6、S7-R5、UA-E1、MSTP-R3/R7/E1、IEC-R10、W-05/W-07/W-15。
- **做法**：成本最低，建议穿插在 W1~W4 里顺手做，不单独占一波。

### G-DOC · 清单标注纠偏 31 条（S · 中 · B）

- **分布**：data-pipeline 8 / read-write 11 / protocol-family 10 / reload-inflight 2。
- **做法**：不单独成批——改哪条测试就顺手把那条清单标注改对；只是行号漂了但按函数名还能找到的，加个注记就行。
- **为什么值**：标注过时会给人「有测试盯着」的假安全感，本身就是债。
- **状态**：✅ 2026-11-26 已纠正。四份清单共 31 处待纠，实际改写 27 行；W-09、TCP-09、G-04、G-05 复核后与现状一致，保持原样。
