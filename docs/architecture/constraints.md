## 9. 关键设计约束

| 约束 | 说明 |
|---|---|
| 配置加载失败必须返回错误 | 不可静默忽略，确保首次落盘可观测 |
| OTA 升级必须检查状态并加锁 | 禁止并发写同一分区 |
| 磁盘满入队检查 `disk_full` + 退避 | 未到退避期直接丢弃，防 CPU 浪费 |
| Web 默认 `127.0.0.1:8080` | 默认仅回环；网线直连调试需显式改 `0.0.0.0:8080` 并先设置 `password_hash`（否则 fail-closed 拒绝启动） |
| `api_token` 为空自动生成随机 token | 保障鉴权安全 |
| 前端产物 500KB–1MB（gzip） | 适应 ARM CPU / 256MB–2GB 内存 |
| 前端离线可用，无 CDN | 直连调试无外网场景 |
| 协议插件化 | 新增协议只需 `ProtocolRegistry::register` |
| 采集与处理解耦 | mpsc 通道，采集周期不受边缘处理耗时影响 |

## 10. 锁与同步原语使用准则

项目使用 4 种同步原语，各有适用场景。新代码必须遵循以下准则：

### ArcSwap — 只读快照热更新
- 适用：配置热更新、需要无锁读取的共享不可变数据
- 特点：读取无锁（`load_full` 返回 `Arc` 快照），写入用 CAS 原子替换
- 项目实例：`AppState.config.config: ArcSwap<GatewayConfig>`
- 禁止：用于需要写入后立即读取最新值的场景（应用 `Mutex`）

### parking_lot::Mutex — 短临界区同步
- 适用：临界区内无 `.await`、持锁时间短的同步场景
- 特点：不中毒（panic 后仍可用）、性能优于 `std::Mutex`
- 项目实例：`Gateway.bus_managers`、`Gateway.mqtt`
- 禁止：临界区内有 `.await`（会阻塞 runtime worker 线程）

### tokio::sync::Mutex — 需要 await 持锁
- 适用：临界区内需要 `.await` 的异步场景
- 特点：async 感知，持锁期间不阻塞 runtime
- 项目实例：`Gateway.reload_lock`、`AppState.config.config_reload_lock`
- 禁止：短临界区（相比 `parking_lot` 有额外开销）

### parking_lot::RwLock — 读多写少
- 适用：读操作远多于写操作的共享可变状态
- 特点：读锁可并发，写锁独占
- 项目实例：`pipeline::point_cache::PointCache`、`north::mqtt` 点位配置快照
- 禁止：写操作频繁（写锁饥饿读锁）

### 选择决策树
```
需要热更新只读快照？→ ArcSwap
临界区内有 .await？  → tokio::sync::Mutex
读远多于写？         → parking_lot::RwLock
其他短临界区？        → parking_lot::Mutex
```

## 11. 非目标声明

> 本节记录**当前形态下明确不做的事**。这些不是"还没来得及做"，而是**经过权衡后的产品边界**。
> 每条都给出重新评估的触发条件——触发条件出现时，本节应被重新讨论，而不是被当作缺陷修复。

### 11.1 形态边界

| 非目标 | 当前形态 | 重新评估触发条件 |
|---|---|---|
| **不做云平台** | 网关完全自治运行：配置在本地 `config.json`，历史数据在本机 SQLite，无中心服务 | 客户要求跨网关统一设备台账、远程批量下发配置，或远程集中监控 |
| **不做双机热备 / 高可用** | 单进程 `gatewayd` + systemd；崩溃由看门狗重启，掉电由硬件看门狗拉起 | 客户明确提出采集不中断的 RTO/RPO 指标，或单站点采集量已到单机瓶颈 |
| **不做集群 / 多实例** | 单网关单实例；配置与队列均为单份 | 客户要求单组站点用多台网关分摊点位 |
| **不做多租户** | 单网关一套配置，配置与数据物理隔离天然满足 | 单客户需在同一网关上运行多套互不影响的配置 |
| **不做异地备份** | 历史数据唯一副本在本机 `data_queue.db`；`.bak` 与主库同盘 | 客户合同含数据留存 SLA / 审计要求（此时出路是定期导出，见 `data-flow.md` §7.3） |
| **不做本地多副本** | 目标为低成本工控板，无冗余存储硬件（无 RAID / 双盘镜像） | 目标硬件引入冗余存储 |

### 11.2 能力边界

| 非目标 | 当前形态 | 重新评估触发条件 |
|---|---|---|
| **不做经营看板 / BI / 报表平台** | Web 控制台定位是「参数配置 + 现场调试」，不是数据驾驶舱 | 客户要求趋势分析、报表生成、看板大屏 |
| **不做自动固件分发** | OTA 接收侧完整（A/B 分区 + Ed25519 验签 + 失败回滚），但**固件靠人工送达** | 客户设备数量增长到人工 scp 不可接受（届时补 `deploy/upgrade.sh` 之外的推送通道） |
| **不做远程批量配置下发** | 配置在 Web 控制台本地修改，写回本地文件 | 客户要求一次改动下发到多个站点 |
| **不做前端工程化平台化** | Vue3 + Vite 单应用，产物离线自托管、无 CDN | 前端需要被嵌入第三方系统或做成可复用组件库 |

### 11.3 为什么显式写下来

- **对客户**：避免"我以为有备份""能不能两台互备""能不能多个厂区统一管"这三类预期落差。
  交付检查单会把相关结论打印出来供签字留档。
- **对开发**：避免把设计决策误当成待补的缺陷；也避免在人员流动后丢掉这些判断的依据。
- **对 CI**：本节由 `scripts/deploy_lint.ps1` 的 C21 段守护（章节存在 + 四条形态边界齐全），
  防止后续被静默删除。
