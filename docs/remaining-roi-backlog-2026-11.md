## 1. 工作量怎么算（人话对照）

| 记号 | 人话 | 典型内容 |
|---|---|---|
| **小** | 半天到 1 天，改一个文件里的一个函数 + 补几条测试 | 改常量、改判定条件、补计数器 |
| **小-中** | 1~2 天，改一个文件 + 同步改前后端契约 | 加一个字段、加一条接口字段 |
| **中** | 3~5 天，跨 2~3 个模块，要动数据结构或配置格式 | 改调度算法、加配置项、加模型字段 |
| **中-大** | 1 周左右，要重新设计一块逻辑 + 补大量测试 | 改重载语义、改指标体系 |
| **大** | 1~2 周以上，触及调度/生命周期主链路，要考虑并发与回滚 | 热重载原子化、文件监听 |

## 2. 清单主体（按 ROI 从高到低排）

### 🟢 A 档：立刻能做，小投入、大回报

#### ✅ ROI-01 让「为什么坏」跟着数据一起走（R-1）
- **现在的毛病**：设备读失败了，网关上报的报文里只写了一句「采集失败」。到底是设备不在线、报文校验错、还是协议格式不认，全被压成同一句话，真正的原因只打印在 debug 日志里（默认看不见）。
- **现场会看到什么**：平台侧看到一片「采集失败」，但分不清是哪类故障；只能到现场抓包。**更糟的是**：如果原因是「报文格式错」，运维会误判成「设备掉线了」，方向一错就白折腾一天。
- **工作量**：**小**。改一个函数（把真实错误原因带进质量原因字段）+ 补几条测试。约半天。
- **价值**：**高**。现场排查从「靠猜」变成「一看就知道坏在哪一环」，直接砍掉大部分返工时间。这是整个清单里性价比最高的一项。
- **依赖**：无。可以第一个就做。
- **现状**：✅ 已完成（`600ebc0`）。上送的原因现在是 `collect_failed:TIMEOUT` 这种「场景:错误码」，现场能直接看出是超时、校验错还是报文解析错。

#### ✅ ROI-02 旧值要打上「这是旧数据」的标记（R-2）
- **现在的毛病**：某个点这次读失败了，网关会把**上一次成功读到的旧值**继续往上送，而且报文里没有任何强制标记说「这个值是旧的」。质量位虽然有 Bad/Stale，但大多数消费方不看它。
- **现场会看到什么**：上位机把几小时前的旧值当实时值用 —— 电表读数不涨、累计流量对不上，排查时根本想不到是「网关在拿旧值糊弄」。
- **工作量**：**小**。把「陈旧」语义写死进数据点模型和接口契约，前端提示一下。约 1 天。
- **价值**：**高**。防止**静默的错误数据**被当成正常数据用掉 —— 这是最坏的一类故障（不报警、结果错）。
- **依赖**：建议和 ROI-01 一起做（同一条链路，一起改省事）。
- **现状**：✅ 已完成（`600ebc0`）。复用旧值时 `raw_type` 标为 `last_good`（从未采到则 `none`）；前端「更新时间」改用真实采集时刻，并提示「采集失败 N 次，显示上次成功值」。

#### ✅ ROI-03 把已经修好的问题在文档里销账（G-01 / G-06 / G-08）
- **现在的毛病**：文档里的「不变量清单」写着 3 个问题「未解决」，但代码其实早就修好了（只是没人回填文档）。另外清单里写的指标名字是错的（`gateway_write_uncertain_total`，实际叫 `gateway_bus_write_uncertain_total`），照着文档去配告警会永远收不到数据。
- **现场会看到什么**：**这个不直接影响现场**，但会让下一个接手的人（包括未来的我们）去「修已经修好的东西」，浪费工时，还可能改坏。
- **工作量**：**小**。改 3 处标记 + 1 处指标名。约 1 小时。
- **价值**：**中高**。零风险、零副作用，但能防止重复劳动和错误告警配置。
- **依赖**：无。
- **现状**：✅ 已完成（`8359f85`）。G-01 / G-06 / G-08 已在清单标为已关闭，指标名修正为 `gateway_bus_write_uncertain_total`。

#### ✅ ROI-04 MQTT 断线降级要真的记一笔数（outbox 降级漏计）
- **现在的毛病**：MQTT 发送队列的数据库打不开时，网关会降级成「只用内存」继续跑。代码注释写着「会记一个降级计数」，但函数根本没拿到计数器句柄，**这个计数其实一直是 0**。Webhook 那条路径记了，MQTT 这条没记。
- **现场会看到什么**：内存模式攒的数据在断电后全没了，但监控上看不到任何异常 —— **丢了数据却没人知道**。
- **工作量**：**小**。给打开函数加一个计数器参数 + 补一处递增 + 一条测试。约半天。
- **价值**：**高**。把「静默丢数」变成「看得见的降级」，是失效可见性的硬门槛。
- **依赖**：无。
- **现状**：✅ 已完成（`a8c836c`）。MQTT 降级时会真的把 `gateway_outbox_degraded_total` 加 1 并打告警日志；同时删掉了 `outbox.rs` 里那句「会递增」的失实注释。

#### ✅ ROI-05 补一份告警规则文件（数据丢弃路径告警）
- **现在的毛病**：网关有一堆计数器（outbox 降级、队列淘汰、持久化丢弃、淘汰告警），但**仓库里没有任何告警规则文件** —— 这些数字被采集了，却没人配规则，于是等于没埋点。
- **现场会看到什么**：数据在悄悄丢，监控上一切正常；等到发现时已经丢了一天。
- **工作量**：**小**。写 4~6 条 Prometheus 告警规则（YAML）+ 一段说明。约 1 天。
- **价值**：**高**。属于「一次投入、长期受益」：以后所有丢数据的问题都能自动报警，不靠人盯。
- **依赖**：建议在 ROI-04 之后做（先有数，再报警）。
- **现状**：✅ 已完成（`a8c836c`）。新增 [deploy/monitoring/prometheus-alerts.yaml](../deploy/monitoring/prometheus-alerts.yaml)，6 条规则可直接接入 Prometheus。

### 🟡 B 档：值得做，投入中等

#### ✅ ROI-06 写下去之前先看一眼值合不合理（W-1 写值域校验）
- **现在的毛病**：写一个点位时，系统只检查「这个点允不允许写」，**不检查写的值合不合理**。比如功率设定点根本没有上下限。
- **现场会看到什么**：任何拿到写权限的上位机 / MES / 脚本，一次手滑就能把设定值写到 3000 kW、压力上限写到 999 bar。**这是真实设备动作**，写下去就要人去复位。
- **工作量**：**中**。要给点位模型加「写入上下限 / 合法范围」字段，配校验逻辑，再决定超范围时是拒绝、限幅还是只报警（**这三种策略要产品口径拍板**）。约 3~5 天。
- **价值**：**高**。防的是「一次误操作 = 一次现场事故」，属于安全类收益。
- **依赖**：**需要先定策略**（拒绝 / 限幅 / 告警），定完就能做。
- **现状**：✅ 已完成（策略选「拒绝写入并报错」）。点位新增 `write_min` / `write_max`（闭区间，留空不限）；越界或 NaN/inf 时单点写入返回 `WRITE_OUT_OF_RANGE 4011`、批量写逐条标失败，**都不下发到设备**；配置页新增「写入范围」输入，配置校验拦截 `min > max`。

#### ✅ ROI-07 坏点要真的退让，别再霸占总线（R-3 退避被拉平）
- **现在的毛病**：设计上有「失败后退避」（1→5→15→60 秒），但退避倍数记在**单个点**上，调度时算周期却取组内**最小**值。结果：只要同组还有一个好点，这个坏点就照样每轮去读、每轮超时，**退避等于没生效**。
- **现场会看到什么**：一台掉线的设备长期霸占总线时隙，把整条总线的有效采集率拖下来；其它设备看起来「时好时坏」，实际是**一个坏点拖垮一条线**。
- **工作量**：**中**。要改调度取周期的算法（取最大退避值，或把退避重灾区拆成独立组）+ 补测试。约 3~5 天。
- **价值**：**高**。直接提升整条总线的有效采集率，属于「一改多受益」。
- **依赖**：建议和 ROI-08（逐点超时）一起设计，两件事共用同一块调度逻辑。
- **现状**：✅ 已完成（方案选「组内跳过未到期的点」）。每轮只读已到重试时间的点：健康点保持原周期，失败点按自己的退避节奏重试；全组都在退避时不占总线、也不伪造失败点。新增 `point_due()` 纯函数与 2 条回归测试。

#### ROI-08 指标要能按「哪台设备 / 哪条总线」看（D-1 指标维度）
- **现在的毛病**：网关有约 75 个指标，但带维度标签的只有一个 —— 而且**只导出失败次数最多的前几个点**。一条总线 200 个点，第 50 名以后的坏点在指标里**完全看不到**。另外没有关联 ID，一次采集的日志串不起来。
- **现场会看到什么**：想查某台设备，只能人工翻日志；坏点排名靠后的，等于压根没被监控。
- **工作量**：**中-大**。现在的指标框架是「固定字段、无标签」，要加维度得先评估基数（设备多不多、点多少），可能引入标签机制并重做部分指标。约 1 周。
- **价值**：**中高**。监控从此能「按设备筛」，但因为要动指标框架（属于对外暴露的接口），改动面偏大，所以排在 B 档而不是 A 档。
- **依赖**：需先做基数评估。

#### ROI-09 批量写要说明白「能不能整批重试」（W-2 批量写语义）
- **现在的毛病**：一次写多个点时，成功和失败混在同一个返回数组里，接口**没有声明**这批是「全成功才算数」还是「可以整批重试」。
- **现场会看到什么**：上游看到 200 但部分失败，就整批重试 → **已经成功的点被写了第二次**。对累加型、脉冲型点位就是重复动作。
- **工作量**：**中**。要在接口契约里声明语义 + 给批量写加幂等键 + 文档说明。约 3~5 天。
- **价值**：**中**。防重复动作，需要上下游一起配合（改接口契约），协调成本比改代码高。
- **依赖**：**需与上游约定**接口语义。

#### ROI-10 给单个从站加「单独观测 + 自动熔断」（G-05）
- **现在的毛病**：Modbus 从站层面的失败情况没有单独的观测指标，也没有「连续失败就暂时跳过它」的机制。
- **现场会看到什么**：坏掉的从站一直被反复访问，既拖慢总线又刷日志；现场只能手工把这个点停掉。
- **工作量**：**中**。加从站维度的失败计数 + 连续失败自动跳过 + 恢复后再接回。约 3~5 天。
- **价值**：**中**。是 ROI-07 的补充（退避解决「多久再试」，熔断解决「要不要还试」）。
- **依赖**：建议在 ROI-07 之后做，两者逻辑相邻。

### 🟠 C 档：价值明确，但改动面大

#### ROI-11 逐点配置超时，别让一个慢设备拖死整条总线（R-4 超时总线级）
- **现在的毛病**：超时时间配在**总线**上。同一条总线上有一台老设备特别慢，工程师只能把整条总线的超时全调大，代价是其它设备出故障时发现得更慢。
- **现场会看到什么**：为了迁就一台设备，全线的故障响应都变迟钝。
- **工作量**：**中-大**。要给点位/设备加超时配置项，改调度预算估算逻辑。约 1 周。
- **价值**：**中**。典型「现场不好受但能忍」，属于优化不是救火。
- **依赖**：与 ROI-07 一起设计。

#### ROI-12 改配置要「要么全生效，要么全不生效」（C-1 热重载原子性）
- **现在的毛病**：改配置时，系统按小节一段段往运行态里套（总线 / 点位 / MQTT / 时间 / 换算…）。如果套到一半失败，**已经套上的那几段不会退回去**；Web 层只会把**磁盘上的文件**回滚，内存里的运行态不回滚。
- **现场会看到什么**：磁盘是老配置、内存是新配置（或者反过来）。**重启前后行为不一样** —— 这是最难查的一类「偶发故障」。
- **工作量**：**大**。要把重载改成「先全量校验 → 生成新快照 → 原子切换 → 失败就整体不动」，涉及运行态生命周期。约 1~2 周。
- **价值**：**中高**。现场「时好时坏、说不清」的疑难故障里，这一类占比不低；但因为不是每天都犯，紧急度排在 B 档之后。
- **依赖**：建议与 ROI-19（并发语义审计）一起做，先审清楚再动。

#### ROI-13 改了配置文件就自动生效，不用重启（C-2 文件监听）
- **现在的毛病**：网关只在「网页上保存配置」时才会重新加载。工程师直接改磁盘上的 `config.json`，**在重启之前完全没效果**。
- **现场会看到什么**：改完发现没用，以为是配置写错了，反复改；或者干脆改完直接重启，撞上 ROI-12 的半生效窗口。
- **工作量**：**大**。引入文件监听依赖 + 处理「文件写到一半被监听到」的常见坑 + 平台差异（Windows / Linux / 嵌入式文件系统）。约 1~2 周。
- **价值**：**中**。属于「体验优化」，不是故障修复。嵌入式设备上文件监听还有功耗和可靠性代价，需要评估。
- **依赖**：建议放在 ROI-12 之后 —— 先保证「重载本身是安全的」，再谈「自动触发重载」。

#### ROI-14 让 Modbus 的多个从站组同时干活（S2 组间串行）
- **现在的毛病**：Modbus 读路径按（从站，功能码）分组，**组内已经并发了**，但**组与组之间是一个一个串行跑的**。
- **现场会看到什么**：从站多的现场（比如 30 台设备在一条总线上），采集一轮要等很久才轮完，周期被拉长。
- **工作量**：**中-大**。要把组间也改成并发，同时保证同一条物理总线上的时序不会乱（RS485 同一时刻只能有一个从站应答）。约 1 周。
- **价值**：**中**。收益**强依赖现场从站数** —— 从站少就基本没收益。
- **依赖**：**需先确认现场典型从站数**，否则可能白干。

#### ROI-15 写属性建模：区分「设定值 / 增量 / 脉冲」（W-3 / G-04）
- **现在的毛病**：点位没法声明「这个点写进去是设定值、是增量、还是脉冲」，读回核对只覆盖了设定值这一种。
- **现场会看到什么**：增量型点位被上层用「多次写」模拟时，读回比对必然对不上 → 操作员每次都得人工读回核实。
- **工作量**：**中-大**。要改点位模型 + 各协议的写路径 + 读回消歧逻辑。约 1 周。
- **价值**：**中**。前提是现场真的用到增量 / 脉冲点位，用得少就不划算。
- **依赖**：**需先确认现场是否真有这类点位**。

### 🟣 E 档：三份文档新查出的具体缺陷（ROI-19 ~ ROI-27）

来源：ROI-16 / ROI-17 / ROI-18 三份文档在梳理过程中**直接查出的代码缺陷与测试缺口**，不是泛泛建议 —— 问题位置已经确定，实施成本比从零排查低得多。

#### ROI-19 失败点的时间戳和值要统一，别一会儿是 0 一会儿是 1970（I-08 / I-56）
- **现在的毛病**：采集失败有两条构造路径。一条复用上次成功值（`Err` 路径，`source_ts` = 上次成功时刻）；另一条（`Ok` 但质量为 Bad）把 `source_ts` 置 0、值置 0、且不复用 last_good。
- **现场会看到什么**：平台收到一部分失败点，**值是 0、时间戳是 1970-01-01**。看起来像设备真的回了 0（功率 0、压力 0），上层按正常数据入账；曲线在断线时段画成一条贴地的 0 线，而且和「复用旧值」的点混在一起，**没法用统一规则判真假**。
- **工作量**：**小-中**。统一 `DataPoint` 的失败构造口径（一条路径）+ 补时间语义契约测试。约 1~2 天。
- **价值**：**高**。属于「静默的错误数据」，且与 ROI-02 的旧值标记自相矛盾（有的失败点标 `last_good`、有的不标）。
- **依赖**：无。

#### ROI-20 串口在途写被重载取消时，不能报「明确失败、可安全重试」（U-1 / U-2）
- **现在的毛病**：reload 重建总线时旧总线任务被丢弃，串口在途写的调用方收到 `BusClosed`；而 `BusClosed` 在 `write_outcome` 里被固定归为「明确失败」（可安全重试）。但帧**可能已经写到线上了**。
- **现场会看到什么**：正在下发控制命令时有人保存了配置 → 命令可能已生效，接口却回「失败，可重试」→ 上位机重发 → **累加型 / 脉冲型点位被重复执行**。
- **工作量**：**中**。给总线事务加「是否已下发」标记，取消时按标记回送 `WriteUncertain`（对应 5102）；或按 ROI-12 的总线级门控（停止收新写 → 有界 drain → 替换 → 恢复）一并解决。约 3~5 天。
- **价值**：**高**。安全类收益：防重复动作，与 ROI-09（批量写语义）同源。
- **依赖**：**建议随 ROI-12 一起做**（最小原子化边界已由 ROI-18 给出）。

#### ROI-21 OPC UA 单点 Bad 不该拆掉整条会话（UA-E2）
- **现状**：✅ 已完成。单点读在 server 响应后先 `record_read_ok`，`extract_value` 失败只降级该点、不再 `record_read_failure`；Bad/Uncertain 统一填 `opcua_status_<StatusCode>:OTHER`（前缀避开北向细分关键字，后缀可被 `from_code` 还原）。回归测试 `opcua/tests.rs:312/335/347/371`（含真实服务端：连续读坏点不拆会话）。详见 [protocol-family-invariants.md](architecture/protocol-family-invariants.md) UA-E2 行。
- **现在的毛病**：单节点取不到值时走的也是 `record_read_failure`，与「整条链路读失败」共用同一个计数器；达到阈值就拆会话重建。
- **现场会看到什么**：某个点位权限不足 / 已被设备删除 → 连续刷新把**整台设备**的会话拆掉，连带其它点位周期性闪断；页面只看到质量 Bad、没有原因，运维只能反复重连。
- **工作量**：**小-中**。区分「单点失败」与「链路失败」两类计数，单点失败只降级该点质量、不计入拆会话阈值。约 1~2 天。
- **价值**：**高**。现场高频且难归因：一台设备的「一个点位」问题被放大成「整台设备掉线」。
- **依赖**：无。

#### ROI-22 IEC101 要校验链路地址 / 公共地址，解码失败要如实上报（IEC-R6 / IEC-R7 / IEC-E2）
- **现在的毛病**：收到应答后**不比对链路地址与公共地址**，直接按 IOA 填值；ASDU 解码失败被吞成 `NoReply`。
- **现场会看到什么**：同一网段内别的站发来的数据被当成自己的值填进缓存，**数值看起来完全合理**，不会触发任何告警 —— 这是这 6 个协议里最晚才会被发现的故障类型。
- **工作量**：**中**。补地址比对（能拿到标识就必须比）+ 解码失败映射到 `InvalidFrame` 而非 `NoReply`。约 3~5 天。
- **价值**：**高**。错站数据是「静默错误」，代价是现场数值全错却无人察觉。
- **依赖**：无（与 ROI-26 同属「应答归属校验」口径，可一起做）。

#### ROI-23 MQTT 的 `qos` 配置项要么生效，要么下线（I-49）
- **现状**：✅ 已完成（选择「下线其它取值」）。`validate_qos` 只接受 1，0/2 在配置校验阶段返回 `invalid_qos`；发布与 outbox 仍恒为 QoS1。前端 QoS 选项同步收敛为「1 - 至少一次（固定）」。测试 `config/mqtt.rs:320`。详见 [data-pipeline-invariants.md](architecture/data-pipeline-invariants.md) I-49 行。
- **现在的毛病**：配置里的 `qos` 只做合法性校验，实际发布**恒为 QoS 1**，outbox 记录的 `qos` 也固定写 1。
- **现场会看到什么**：配置里写 `qos: 2`，broker 实测却是 QoS 1；按 QoS2 的「恰好一次」语义设计幂等链路的人会判断错误，**而且日志里看不出来**。
- **工作量**：**小**。二选一：让 `qos` 真正参与 publish（需评估 QoS2 与现有保序假设的兼容性），或删掉该配置项并在文档说明「恒为 QoS1」。约半天~1 天。
- **价值**：**中**。配置契约层面的静默偏差，现场几乎无法自证。
- **依赖**：无。

#### ROI-24 虚拟点缓存的值要统一用「上报口径」（I-28）
- **现状**：✅ 已完成。`update_cache` 只写 `final_points` 中仍为 Good 的上报口径值；被边缘过滤或质量降级的点保留上一条上报口径值，绝不回退到 convert 前的 `items.value`。测试 `pipeline/virtual_point.rs:552/566/584`。详见 [data-pipeline-invariants.md](architecture/data-pipeline-invariants.md) I-28 行。
- **现在的毛病**：虚拟点缓存里，**只有本批通过过滤且仍为 Good 的点**用换算后的值；被死区 / 变化阈值 / 聚合过滤掉、或被质量规则降级的点，缓存回退成**换算前**的原始值。
- **现场会看到什么**：同一个采集点在不同批次给虚拟点提供的量纲不一致 → 派生值忽大忽小，或与平台收到的上报值对不上，**看起来像公式写错了**，其实公式没错、是喂进去的数换了口径。
- **工作量**：**小-中**。统一缓存写入口径（虚拟点只存最终上报口径值）+ 补口径一致性测试。约 1~2 天。
- **价值**：**中高**。「派生值对不上上报值」是虚拟点类问题的高频根因。
- **依赖**：无。

#### ROI-25 读路径的「设备明确拒绝」要单独一种错误码（跨协议共性）
- **现在的毛病**：MC 1E 帧、FINS TCP、S7 读、MS/TP、IEC101 里，设备明确拒绝都被压成 `InvalidFrame`（对外显示 `DECODE`）；而读路径的 `read-write-invariants.md` W-03c 只对写路径要求用 `DeviceRejected`。
- **现场会看到什么**：现场看到「解码错误」，就去查接线和波特率；实际是**设备明确拒绝了这个请求**（地址越界、功能码不支持、权限不足）—— 方向一错就白折腾一天。
- **工作量**：**中**。统一错误映射口径（5 个协议族逐个对齐）+ 补映射测试。约 3~5 天。
- **范围提醒**：`FINS` 与 `BACnet MS/TP` 已是「退役观察」（不在默认编译集 `all-protocols`），实际只需改 **MC / S7Comm / OPC UA / IEC101** 四族，工作量降到约 2~3 天。
- **价值**：**中高**。与 ROI-01 同类收益：把「靠猜」变成「一看就知道坏在哪一环」。
- **依赖**：需先统一口径（W-03c 的规则扩展到读路径）。

#### ROI-26 应答归属校验口径统一：能拿到标识就必须比（跨协议共性）
- **现在的毛病**：MC 的 3E/4E 不校验站号与网络号回显、FINS UDP 无匹配、S7 不校验 PDU ref、MS/TP 不校验应答源地址、IEC101 不校验链路 / 公共地址 —— 只有 S7Comm 一族做了写值范围校验（MC、FINS 也缺）。
- **现场会看到什么**：串包 / 串台时**把别人的应答当自己的值**，值本身合法、看着正常，**没有任何告警**。
- **工作量**：**中-大**。5 个协议族逐个补「能拿到标识就必须比」的校验 + 补测试。约 1 周。
- **范围提醒**：同样受退役观察影响，实际必做的是 **MC / S7Comm / OPC UA / IEC101** 四族（FINS、MS/TP 只在显式启用时才需要）。
- **价值**：**中**。批量、并发场景下收益明显；现场单从站场景基本无感。
- **依赖**：与 ROI-22 同批做；建议先确认现场从站数与是否多主站（见 ROI-14）。

#### ROI-27 把三份文档里的测试缺口补成守护用例
- **现在的毛病**：数据链路 20 条不变量（17 条完全无守护 + 3 条部分守护）、协议族 39 条不变量**只靠代码约定维持**，没有自动化断言。清单已经把它们列出来了，但没有一条变成用例。
- **现场会看到什么**：**本身不直接产生故障**，但下一次改 pipeline / 换算 / 协议写路径时，没有回归网兜底 —— 同一个坑换个协议再踩一次。
- **工作量**：**中**。按 ROI-17 的缺口汇总表与 ROI-16 的逐族表格逐条补断言，优先级 I-08 / I-28 / I-49 → OPC UA 读路径 → IEC101 地址归属。约 3~5 天（可拆多批）。
- **价值**：**中**。一次性投入、长期受益，是这批新增项里最「防未来」的一条。
- **依赖**：无，可与其它项并行。
