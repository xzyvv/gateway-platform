## 2. 分场景说明

### 2.1 冒烟与小规模（50 / 800 点）

- 50 点：吞吐 51.8 点/秒，p99 4.83 ms，RSS 33.4 MB —— 现场小点数场景的参考基线。
- 800 点 / 8 并发：吞吐 795.1 点/秒，RSS 28.6 MB，零失败 —— 适合作为 CI 门禁的最小规模。

### 2.2 规模扫描（2 000 → 20 000 点，sweep L1~L5）

| 档 | 点位 | 从站数 | 吞吐(点/秒) | 相对 L1 | CPU 峰值 |
|---|---|---|---|---|---|
| L1 | 2 000 | 1 | 2 008.6 | ×1.00 | 0.4 % |
| L2 | 2 000 | 200 | 2 006.4 | ×1.00 | 1.3 % |
| L3 | 8 000 | 200 | 8 027.5 | ×4.00 | 4.3 % |
| L4 | 20 000 | 200 | 14 245.4 | ×7.09 | 8.0 % |
| L5 | 20 000 | 200 | 13 555.3 | ×6.75 | 7.7 % |

- L1（1 从站）与 L2（200 从站）同点数下吞吐几乎相同 → 从站数量本身不构成瓶颈，**点位规模才是**。
- L1 的 p50 仅 3.62 ms，L2 升到 300 ms（200 个从站分散成更多帧、每轮事务数上涨）；
  这是「同样 2 000 点、报文形态不同」的延迟差异，不代表吞吐退化。
- L3→L4 吞吐增益 ×1.78，L4→L5（并发 8→64）为 ×0.95 → **tcp 并发超过 8 不再带来收益**，
  与 [perf-knee.md](perf-knee.md)「`tcp_concurrent = 8` 是性价比最优值」结论一致。
- L3 起队列深度触顶 1 000 000（见 §3）。

### 2.3 8 000 点定点复测（L3 系列）：1 并发正常，8 并发整轮失败

| 场景 | tcp 并发 | 吞吐(点/秒) | 失败 | p50/p95/p99 |
|---|---|---|---|---|
| perf-L3-t1 | 1 | 7 973.9 | 0 | 684.78 / 968.48 / 993.70 ms |
| perf-L3-t8 | 8 | 1 305.7 | 64 000 / 72 000 | 1000 / 1000 / 1000 ms |
| perf-L3-t8b（同参数复测） | 8 | 1 014.5 | 64 000 / 64 000 | 1000 / 1000 / 1000 ms |

- **归因**：单轮批量读取耗时超过调度器的 **5s `read_batch` 超时**，该轮全部点位被判失败；
  报告里「吞吐 1 000+ 点/秒」实为失败点位的计数，不是有效采集。
  详细机制与经验公式见 [perf-knee.md §调优建议](perf-knee.md)（`tcp_concurrent ≳ (单轮点数 × 单帧耗时) / 2s`）。
- 两次复测结果一致（64 000 全失败），说明这是**参数配置触发**的稳定故障，而非偶发抖动。
- 运维含义：8000 点规模下 `tcp_concurrent` 不能设为 8；同时队列深度触顶后失败会叠加。

### 2.4 20 000 点定点复测（L4 系列）

- 吞吐 14 245 ~ 19 896 点/秒，零失败；p99 全部饱和在 995~1000 ms。
- RSS 增长 30.3 ~ 53.4 MB，**不是泄漏**：压测未配置北向消费，采集数据全部堆在 SQLite
  page cache / WAL buffer（30 秒约 52~62 万行）。量化估算与生产收敛条件见
  [perf-rss-explanation.md](perf-rss-explanation.md)。
- L4-t1（1 并发）17 523 点/秒 与 L4-t8（8 并发）19 896 点/秒 相差约 14%，说明并发从 1 提到 8 仍有收益；
  与 §2.2「并发超过 8 无增益」并不冲突（8 是拐点，不是起点）。两者采集行数不同（54 万 vs 64 万），
  该差异部分来自采样窗口，方向性结论以 §2.2 的 L4 / L5 对照为准。

## 3. 读数口径（必读）

| 现象 | 含义 |
|---|---|
| 队列深度峰值 = **1 000 000** | 触发队列上限截断（100 万条），实际深度只会更高，不能当作真实峰值 |
| 延迟 p50/p95/p99 = **1000.00 ms** | 直方图最大有限桶饱和，表示单轮耗时 ≥ 1s，无法分辨更细差异 |
| RSS 增长为正且队列深度持续上涨 | 「未配置北向消费」的预期行为，非泄漏（见 [perf-rss-explanation.md](perf-rss-explanation.md)） |
| 失败数 = 采集次数 | 整轮被判超时失败，吞吐数字失真（见 §2.3） |
| 吞吐上限 ≈ 150 000 点/秒 | mock 从站与网关同机争抢 24 核 CPU，此为两者合计上限，非网关能力上限（见 [perf-knee.md](perf-knee.md)） |

## 4. 复现命令

```powershell
# 单档复现（示例：20 000 点 / 8 并发 / 0.5 min）
python gateway-core/scripts/perf_baseline.py `
  --points 20000 --slaves 200 --tcp-concurrent 8 `
  --duration-min 0.5 --sample-sec 5 --no-build `
  --target $env:CARGO_TARGET_DIR --output docs/perf-run.md

# 规模扫描（§2.2 的 L1~L5 未提供 sweep 参数，逐档改 --points / --slaves 单独运行后并入汇总表）
python gateway-core/scripts/perf_baseline.py `
  --points 2000 --slaves 200 --duration-min 2 --sample-sec 4 --no-build `
  --target $env:CARGO_TARGET_DIR --output docs/perf-run.md

# 总线 × 并发矩阵扫描（perf-knee 使用）
python gateway-core/scripts/perf_baseline.py `
  --sweep-buses "2,4,8,16" --sweep-tcp "8,16,32" `
  --points 150000 --slaves 200 --duration-min 0.35 --sample-sec 4 --no-build `
  --target $env:CARGO_TARGET_DIR --output docs/perf-run.md
```

> 脚本默认 `--output` 即 `docs/perf-baseline.md`。新压测请先输出到 `docs/perf-run.md`，
> 再把结果并入本文件 §1 汇总表，避免整份历史基线被单次运行覆盖。
