# 网关性能拐点（knee）压测报告

生成时间：2026-10-14 23:30:54（数据）／2026-10-14 23:45（结论）

## 结论摘要（TL;DR）

| 项 | 结论 |
| --- | --- |
| 本机实测吞吐上限 | **≈ 150 000 点/秒**（16 条总线，150 000 点/轮，零失败） |
| 单条总线吞吐 | ≈ **26 000 点/秒**（2 总线档反推），与早期单总线 32 000 点/秒一致 |
| 拐点位置 | 总线数 **8→16** 之间：吞吐增益从 1.52× 骤降到 1.08×，整机 CPU 达 **87%→98%** |
| 网关自身瓶颈？ | **否**。峰值时网关仅用 **≈ 10 / 24 核**（45%），整机却已 98% |
| 真正的天花板 | **测试机自身**——内置 mock 从站与网关抢同一台 24 核机器的 CPU |
| `tcp_concurrent` 是否越大越好 | **否**，8 已足够：8/16/32 三档吞吐完全持平 |

> 一句话：**在本台机器上，网关吞吐 ≥ 150 000 点/秒，且该数值尚未触及真实上限**。
> 测不到更高不是网关的能力问题，而是 mock 从站和网关共用同一台机器的 CPU。

## 方法

- 点位：**150 000**（策略：`slaves=200` 打散从站、地址步长 8 > merge gap 5 → **每点独立成帧、事务数 ≈ 点数**，即总线最坏情形）
- 采集周期：1000 ms；每档运行 0.35 min、采样 4s；**去掉启动态**（Web 就绪后才开始计时）
- 维度：`buses ∈ {2,4,8,16}`（每总线一条独立 TCP 连接）× `tcp_concurrent ∈ {8,16,32}`（单连接在途事务上限）
- 解除测试端瓶颈：每条总线配**一个独立的 mock 从站进程**（`--mock-procs = buses`），避免单进程 Python GIL 天花板
- 判定口径：**一轮耗时 = 点数 / 吞吐**
  - 一轮耗时 ≤ 采集周期 ⇒ 该档被周期封顶（测不出总线上限）
  - 吞吐随并发停涨 / 延迟分位陡增 / CPU 逼近饱和处即为**拐点**

### 吞吐随总线数的缩放（tcp=16 档）

| 总线数 | 吞吐(点/s) | 相对上一档增益 | 单总线吞吐 | 整机 CPU |
| --- | --- | --- | --- | --- |
| 2 | 52 285 | — | 26 143 | 37% |
| 4 | 90 968 | ×1.74 | 22 742 | 55% |
| 8 | 137 239 | ×1.51 | 17 155 | 88% |
| 16 | 148 364 | **×1.08** | 9 273 | 98% |

**单总线吞吐随总线数增加而下降**（26k → 9k），说明并非网关单连接能力不足，
而是**总线数越多，mock 进程与网关争抢 24 核 CPU 越激烈**，单总线能分到的算力被摊薄。

## 拐点判定

- **全局最大吞吐：148 642 点/秒** @ buses=16, tcp=32（一轮 1.01s，网关 CPU 10.0 核，整机 96%）
  - 该档一轮耗时 ≈ 采集周期，**处于周期封顶边缘**；但此时**整机 CPU 已 96%~98%**，
    即使增加点数解除周期封顶，也只会撞上机器算力墙，不会明显更高。
- **拐点（吞吐停涨点）落在 8 → 16 总线之间**：增益由 ×1.51 掉到 ×1.08，
  且整机 CPU 由 88% 升至 98%。
- **`tcp_concurrent` 在 8 以上无增益**：每个总线档内 8/16/32 三档吞吐持平
  （如 2 总线：52 301 / 52 285 / 52 288），说明单连接在途 8 个事务已足以满足该总线 mock 线程的吞吐需求。

## 瓶颈归因

- 全矩阵网关 CPU 峰值约 **10.7 / 24 核（45%）**；整机 CPU 峰值约 **98%**。
- **判定：整机 CPU 已近打满，瓶颈在共享的测试机上**——网关与其内置多进程 mock 争抢同一台机器的 CPU。
  - 网关自身仅用 ~10.7/24 核，**远未饱和**；结论是「**网关吞吐 ≥ 本报告峰值 150 000 点/秒**」，
    真实上限需把 mock 放到独立机器（或大幅提高 mock 效率）才能继续逼近。
- 反证：若瓶颈在网关，网关 CPU 应随 GE 递进逼近 24 核；实测稳定在 ~10 核，而整机先到 98%。

## 调优建议

1. **`tcp_concurrent = 8` 是性价比最优值**，无需调大（8/16/32 实测持平）。
2. **单总线吞吐约 26 000 点/秒**；现场若单总线点位规模大，应**拆多总线**分摊（每增一条总线 ≈ +1 个采集 task +1 条 TCP 连接）。
3. **`tcp_concurrent` 不可过低**（重要运维约束）：
   本次预实验用 `buses=1, tcp=1, 150 000 点` 时，单轮批量读取超过调度器的 **5s `read_batch` 超时**，
   导致该轮 **全部点位被判失败**（`gateway_collect_failures` 暴涨且吞吐「看似」很高——那是失败点位的计数）。
   即：**点位规模 × 单帧耗时 / tcp_concurrent 必须明显小于 5s**，否则整轮采集归零。
   经验公式：`tcp_concurrent ≳ (单轮点数 × 单帧耗时) / 2s`。

## 残余限制与未测项

1. **mock 从站仍是共同瓶颈**：内置 mock 为纯 Python，单连接单线程；虽已每总线一进程，
   但其 CPU 与网关同机竞争，150 000 点/秒 已是**两者合计**的上限，非网关单方面能力。
2. **无北向消费**：本压测未启用 MQTT，采集数据全部堆在本地存储队列（`queue_depth` 峰值 ≈ 115 万行），
   实测 RSS 随运行增长（≈ +60 MB / 5s）。生产环境由北向消费队列，存储压力低于本压测，
   因此本报告数值是**偏保守**的下界估计。
3. **延迟分位在高压档饱和**：`p50/p95` 达到直方图最大有限桶 1000 ms，
   说明单轮批量读取耗时 ≥ 1s，无法分辨更细的延迟差异；如需精确延迟应按「单事务」而非「单轮批次」埋点。
4. **未测更高总线数**：16 总线已令整机 98%，再增总线只会加剧争抢，故未继续上探。

## 复现命令

```powershell
$env:CARGO_TARGET_DIR = "<target-dir>"
python gateway-core/scripts/perf_baseline.py `
  --sweep-buses "2,4,8,16" --sweep-tcp "8,16,32" `
  --points 150000 --slaves 200 --duration-min 0.35 --sample-sec 4 `
  --no-build --target $env:CARGO_TARGET_DIR --output docs/perf-knee.md
```
