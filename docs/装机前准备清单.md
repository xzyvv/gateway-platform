# 装机前准备清单（面向现场工程师）

面向**到现场执行装机的人**。目标：在动手装之前把「装完必然踩的坑」全部消掉，
让 `sudo bash deliver.sh` 一次跑通、检查单全绿。

> 本文只讲**装机之前**要准备什么。装中/装后的排障见
> [`故障处置卡.md`](故障处置卡.md)；许可证的签发顺序依赖见
> [`license-签发流程.md`](license-签发流程.md)。

---

## 0. 一分钟总览

装机前必须同时满足下面 6 组条件，缺任意一组都会在装完才暴露，且**现场没有回滚条件**：

| 组 | 条件 | 缺了会怎样（现场现象） |
|---|---|---|
| A 软件产物 | 交付包完整（`gatewayd` + `ui-dist` + 4 个脚本 + unit + 模板） | 装到一半才报「找不到 xxx」 |
| B 系统前置 | root、`systemctl`、`curl` 可用 | 脚本第 0 步就退出 |
| C 硬件接法 | 串口驱动已加载、看门狗/GPIO 节点存在、OTA 分区路径已知 | **服务正常、控制台能开，但硬件功能全是空的**（无报错日志） |
| D 配置 | 一份**完整**的 `config.json`（不是片段示例） | 网关起来了但没有总线/点位，或直接拒绝启动 |
| E 安全顺序 | 先设 `password_hash`，再放开 `listen_addr` | fail-closed，网关**拒绝启动** |
| F 授权 | 许可证按「先装机取码 → 签发 → 导入」的顺序走 | 导入被拒 / 授权看似无效 |

---

## 1. A 组：软件产物（出发前在办公室备齐）

交付包由 `deploy/build-release.sh` 产出。**出发前先解包确认下列文件都在**，
不要到了现场才发现包少东西：

```
gatewayd                # 或 gatewayd-<target>，交叉编译产物
ui-dist/index.html      # 前端静态资源（缺了只剩内置调试控制台）
install.sh              # 安装脚本
deploy-linux.sh         # install.sh 的别名，方便远程执行
serial-rules.sh         # 串口稳定名生成器（4.6 步调用；缺则只能人工保证设备名不变）
verify-deploy.sh        # 部署验证脚本（判定逻辑唯一来源）
deliver.sh              # 一键交付：install → 等待就绪 → verify → 导出检查单
gateway.service         # systemd unit
templates/builtin/      # 内置设备模板
config.factory.json     # 出厂完整配置模板（兜底用）
```

**关键点**

- `ui-dist/index.html` 必须存在。`build-release.sh` 打包前会先 `rm -rf` 旧 `ui-dist`，
  正是为了避免 `dist` 被嵌套成 `ui-dist/dist` 导致 `index.html` 找不到
  （见 `deploy/build-release.sh` 的 `[3/3] 打产物包`）。
- `config.json.example` **不是**配置文件。`gateway-core/config.json.example` 是
  「配置片段示例」，缺 `buses`/`points`/`mqtt` 等必填段，文件自身也写明不会被加载；
  拿它当整份 `config.json` 会得到一份没有 `web` 段的配置。完整可加载的初值是
  `config.factory.json`。
- 若交付方**随包提供现场定制的 `config.json`**，它优先级高于 `config.factory.json`；
  `install.sh` 的 5 步会优先拷贝包内 `config.json`，找不到才用出厂模板。

## 2. B 组：系统前置条件

`install.sh` 在动手前会自检以下几项（源码 `gateway-core/deploy/install.sh` 前置自检段），
**现场先自查一遍能省掉一次返工**：

```bash
id -u                      # 必须为 0（root），否则脚本直接退出
command -v systemctl      # 必须存在
command -v curl           # 必须存在
```

| 依赖 | 缺失后果 | 现场处置 |
|---|---|---|
| root 权限 | 脚本第一步退出，无法装 `/opt/gatewayd`、`/etc/gateway` 与 systemd 服务 | `sudo bash deliver.sh` |
| `systemctl` | 无法装/启服务 | `apt-get install -y systemd` |
| `curl` | 健康检查跑不了，安装末尾判「健康检查未通过」 | `apt-get install -y curl` |
| `python3` | 可选但**强烈建议有**。`install.sh` 用它解析 `config.json` 的 `web.listen_addr` 来定位健康检查端口；缺失则退回默认 `127.0.0.1:8080`。若现场改过端口，缺 `python3` 会导致**健康检查打错端口**，被误判成安装失败。`verify-deploy.sh` 的 `[6b] 总线 port_name` 段也依赖它，缺失时只能 WARN「请人工核对」 | `apt-get install -y python3`；或给 `deliver.sh` 传 `--port <真实端口>` 固定探测端口 |

**目录与磁盘**（`install.sh` 会自建，无需手工建）

| 路径 | 用途 | 备注 |
|---|---|---|
| `/opt/gatewayd` | 二进制 + `ui-dist` + `serial-rules.sh` | `ProtectSystem=strict` 下**不可写**，运行期不写这里 |
| `/etc/gateway` | `config.json`、模板、`serial-bindings.tsv`、`license.lic` | 在 `ReadWritePaths` 内，**运行期可写** |
| `/var/lib/gateway` | 数据队列库、证书、OTA 暂存、license 时钟库 | 数据盘，容量要够 |
| `/var/log/gateway` | 运行日志 | 与数据同盘时要留余量 |

**数据分区余量**：`verify-deploy.sh` 的 `[1g] 数据留存` 段会在剩余空间 **< 512 MB** 时
报 WARN。磁盘见底时 SQLite 入库会暂停，表现为**数据停采而不是报错**——现场极难定位。
装机前先 `df -h /var/lib/gateway` 看一眼。

> **要算准该配多大的卡、配多大的 `queue.max_rows`**（点位规模 → 每天行数 →
> 磁盘占用 → 选型），见 [`容量规划.md`](容量规划.md)。那里还有五项占用总账
> （原始库 / 备份副本 / 聚合表 / WAL / journald）与磁盘水位四档。
>
> **一个必须提前确认的输入**：每个点位的**实际采集周期**。出厂模板的示例点位是
> `interval = 1`（秒，仅用于开箱验链路，且必须严格小于 `mqtt.publish_interval`），
> 投运前必须按现场要求改；放大到 5 秒磁盘占用就降到 1/5，按示例值估算会显著高配存储。

**日志上限**：`StandardOutput=journal`，日志与数据同盘。没有 `SystemMaxUse` 限额时
journal 会一路涨到磁盘满 → SQLite 入库暂停 → **数据停采而不是报错**。

限额**不在 `gateway.service` 里**——`SystemMaxUse=` 是 `journald.conf` 的 `[Journal]` 段选项，
写进 unit 会被 systemd 忽略（静默不生效，看着配了其实没配）。
`install.sh` 会写 drop-in `/etc/systemd/journald.conf.d/60-gateway-journal.conf`：

```ini
[Journal]
SystemMaxUse=512M     # 持久化 journal 占用上限（/var/log/journal）
SystemKeepFree=1G     # 为数据盘预留的空闲（journald 取两者较小值生效）
RuntimeMaxUse=64M     # 易失 journal 上限（/run/log/journal，内存盘）
```

容量不同的机器可用环境变量覆盖：`GATEWAY_JOURNAL_SYSTEM_MAX_USE` /
`GATEWAY_JOURNAL_SYSTEM_KEEP_FREE` / `GATEWAY_JOURNAL_RUNTIME_MAX_USE`。

装完用 `verify-deploy.sh` 的 `[6d]` 段核对（该段同时查主文件与 drop-in，只查主文件会误报）。

## 3. C 组：硬件接法（最容易漏、后果最隐蔽）

这一组的特点是：**装完看起来一切正常，但对应的硬件功能是空的，日志里还没有报错。**

### 3.1 串口驱动必须提前加载

`gateway.service` 用**设备组形式**放行串口：

```ini
DeviceAllow=char-ttyUSB rw
DeviceAllow=char-ttyS rw
DeviceAllow=char-ttyACM rw
```

**为什么不能写 `/dev/ttyUSB`**：systemd v255 对路径形式会先 `stat(node)`，而
`/dev/ttyUSB` 不是真实节点（真实节点是 `/dev/ttyUSB0`、`/dev/ttyUSB1`…），
stat 失败 → **整条 DeviceAllow 被丢弃** → 程序 `open()` 之前就被 EPERM 拒绝 →
**全部串口协议采集不上来，且没有任何报错日志**。

**设备组的代价**：组名必须在**服务启动那一刻**能在 `/proc/devices` 里解析出来，
也就是驱动模块必须已加载。否则 systemd 解析失败 → 整条丢弃 → 同样的静默失效。

`install.sh` 的 **4.5 步**就是为此：把 `cp210x / ch341 / ftdi_sio / pl2303 / cdc_acm`
里实际存在的模块写进 `/etc/modules-load.d/gateway-serial.conf` 并**立即 modprobe**
（不等下次重启）。同时 unit 里有 `Wants=systemd-modules-load.service`
（静态 unit，只 `After=` 不会激活，必须显式 `Wants=`）保证开机加载。

**现场自查**：

```bash
cat /proc/devices | grep -E 'ttyUSB|ttyS|ttyACM'   # 要能看到对应 major
ls /etc/modules-load.d/gateway-serial.conf
```

`/proc/devices` 里查不到 `ttyUSB` → 服务起不来或串口全废。

### 3.2 串口必须用稳定名，不能填 `/dev/ttyUSB*`

`config.json` 里的 `buses[].port_name` 是**裸字符串**，直接进 `tokio_serial::new()`。
USB 串口的 `/dev/ttyUSB*` 编号由**枚举顺序**决定，重启一次就可能变成
`/dev/ttyUSB0 → /dev/ttyUSB1`。名字对不上 → `open()` 失败 → 该总线静默停摆，
日志里只有「找不到设备」，现场极易误判为硬件坏了。

**正确做法**：用 `install.sh` 的 4.6 步生成的 udev 稳定名。

```bash
sudo bash /opt/gatewayd/serial-rules.sh          # 重跑会保留原有绑定，不洗牌
ls -l /dev/gateway-serial*                        # 稳定名应存在
cat /etc/gateway/serial-bindings.tsv              # 序号 ↔ 物理设备 的绑定记录
```

把 `/dev/gateway-serialN` 填进 `buses[].port_name`。
**不要直接填 `/dev/ttyUSB*`**。判据见 `verify-deploy.sh` 的 `[6b] 总线 port_name` 段：
存在且用了稳定名才 PASS，裸 `/dev/ttyUSB*` 是 WARN。

### 3.3 看门狗与 GPIO 节点

`DeviceAllow` 是**白名单**语义——一旦出现任何 `DeviceAllow=`，未列出的设备一律拒绝，
且拒绝发生在程序 `open()` **之前**。

| 设备 | unit 里已放行 | 代码侧实际打开的路径 |
|---|---|---|
| 硬件看门狗 | `/dev/watchdog`、`/dev/watchdog0`、`/dev/watchdog1`、`/dev/softdog` | 按序探测这 4 个候选（`gatewayd/src/bootstrap/helpers/collection.rs` 的 `WATCHDOG_DEVICE_CANDIDATES`） |
| GPIO | `/dev/gpiochip0` | 硬编码 `/dev/gpiochip0`（`gateway-core/src/platform/gpio.rs`） |

看门狗 4 条候选**必须全放行**：只放 `/dev/watchdog` 而实际是 `/dev/watchdog0` 时，
systemd 在 `open()` 前 EPERM 拒绝 → **看门狗静默失效**，表现为「设备卡死不会被硬件复位」。

GPIO 不放行 → **DI 采集 / DO 输出 / RS485 DE 方向控制全部静默失效**
（GPIO 走独立采集路径，不经过 BusManager）。

**现场自查**：

```bash
ls -l /dev/watchdog* /dev/softdog /dev/gpiochip0
```

### 3.4 OTA A/B 分区路径

默认按 **eMMC** 写死：`/dev/mmcblk0p2`（A 槽）与 `/dev/mmcblk0p3`（B 槽）。
现场用 SD / NVMe 做 OTA 介质时，分区路径会变（`/dev/sda2`、`/dev/nvme0n1p2`…），
**必须同时改两处，缺一 OTA 直接失败**：

1. systemd unit 的 `DeviceAllow=`（不放行 → `open()` 前 EPERM）
2. 进程环境变量 `GATEWAY_OTA_SLOT_A` / `GATEWAY_OTA_SLOT_B`（决定写到哪个分区）

`install.sh` 的 7 步会用这两个环境变量**同时**改写 unit 的 `DeviceAllow` 段与
`Environment=` 行，不要手工只改一处：

```bash
sudo GATEWAY_OTA_SLOT_A=/dev/sda2 GATEWAY_OTA_SLOT_B=/dev/sda3 bash deliver.sh
# 或
sudo bash deliver.sh --ota-slot-a /dev/sda2 --ota-slot-b /dev/sda3
```

### 3.5 设备指纹的稳定性（影响许可证）

许可证绑定的是本机指纹：主键 `/etc/machine-id`，回退项板载 MAC / 存储序列号 /
设备序列号。**换板、换盘、改 `/etc/machine-id` 都会让指纹变化**，已授权设备会被判
`Mismatch`（见 `license-签发流程.md` 与 [`故障处置卡.md`](故障处置卡.md) 卡 2）。

装机时顺手确认 `/etc/machine-id` 是**稳定且非空**的值：

```bash
cat /etc/machine-id        # 容器内是随机值，部署须从宿主机挂载
```

## 4. D 组：配置准备

### 4.1 必须是完整配置

`/etc/gateway/config.json` 需含 `buses` / `points` / `mqtt` / `web` / `license` 等段。
`install.sh` 的 5 步逻辑：

- `/etc/gateway/config.json` **已存在 → 保留原值**（升级不覆盖）
- 包内有 `config.json` → 拷贝它（现场定制优先）
- 包内没有 → 用 `config.factory.json` 兜底（完整可加载，含一条示例总线 + 一个示例点位）
- 两者都没有 → 网关以安全默认值启动（仅 `127.0.0.1:8080`，token 随机生成并打印到 journal）

### 4.2 出厂模板投运前要改的字段

`config.factory.json` 的示例点位 `demo_modbus_1` **仅用于开箱验链路**，投运前必须替换。
按现场改这几项：

| 字段 | 怎么改 |
|---|---|
| `buses[].port_name` | 填 `/dev/gateway-serialN`（见 §3.2），不要填 `/dev/ttyUSB*` |
| `buses[].baud_rate` 等 | 按现场设备实际参数改 |
| `points` | 换成现场点表 |
| `mqtt.enabled` / `broker` | 未接 broker 时**保持 `false`**。开启但没 broker 会让队列持续积压且不断重连 |
| `web.api_token` | 需要固定 token 就填；留空则启动时随机生成并打印在 journalctl |
| `web.listen_addr` | 默认 `127.0.0.1:8080`（仅本机可访问），放开 LAN 见 §5 |

### 4.3 许可证路径必须落在可写目录

`license.path` 决定许可证文件放在哪。解析优先级
（`gatewayd/src/bootstrap/helpers/assemble.rs` 的 `init_license`）：

```
环境变量 GATEWAY_LICENSE_PATH  >  config.license.path  >  默认 ./license.lic
```

**默认的 `./license.lic` 是相对进程 CWD 的**，而 unit 的
`WorkingDirectory=/opt/gatewayd`——`/opt/gatewayd` **不在 `ReadWritePaths` 里**
（`ProtectSystem=strict` 下只读）→ **导入许可证会写盘失败**。

出厂模板已配 `"/etc/gateway/license.lic"`（在 `ReadWritePaths` 内），
**不要改成相对路径**。

## 5. E 组：安全顺序（fail-closed，顺序错就直接起不来）

网关有一条**硬性安全策略**：绑定所有网卡 + 空 `password_hash`（默认凭据 `admin/admin`）
= 硬性违规 → **网关拒绝启动**（不是告警）。判定见
`gateway-core/src/config/web.rs` 的 `security_violations()`，拒绝发生在
`gatewayd/src/bootstrap/helpers/assemble.rs` 的 `bail!`。

**必须按这个顺序做**：

1. **先保持回环监听**（默认 `127.0.0.1:8080`），用默认凭据 `admin/admin` 登录
2. 调 `POST /api/auth/password` 改密码（哈希**自动写回** `config.json`）
3. **再**把 `web.listen_addr` 改成 `0.0.0.0:8080` 并重启
4. 改密后可把 `web.allow_default_token` 置 `false`

> **不能反过来**：先把 `listen_addr` 改成 `0.0.0.0:8080` 而 `password_hash` 还空着
> → 网关启动即被 `bail!` 拒绝 → 现场看到「服务起不来」，但日志里的原因不直观。

另外一条独立的 fail-closed：`web.password_hash` 为空**且** `web.allow_default_token=false`
→ 同样拒绝启动（此时不允许用默认凭据）。

## 6. F 组：许可证（详见 [`license-签发流程.md`](license-签发流程.md)）

装机阶段与许可证直接相关的三件事：

| 事项 | 装机时要做 |
|---|---|
| 签发顺序 | **必须先装机**才能取到设备码（设备码来自本机采集，网关未装无从获取） |
| 导入通道 | `POST /api/license/import`（需 token），或把 `.lic` 文件放到 `license.path` 后重启 |
| 配额 | 无许可证时配额是 **100 点**（`DEFAULT_ABSENT_QUOTA`）。**大批点位要先有许可证**，否则保存配置被拒 |

## 7. 装机执行顺序（照着做，别跳步）

`install.sh` 的实际步骤：

| 步 | 动作 | 现场注意 |
|---|---|---|
| 前置自检 | root / `systemctl` / `curl` | 缺任一直接退出 |
| 1 | 创建系统用户 `gateway`（加入 `dialout` 组） | |
| 2 | 建目录结构 | |
| 3 | 拷贝二进制（先停服再替换，避免 `ETXTBSY`）；顺带装 `serial-rules.sh` 到 `/opt/gatewayd` | |
| 4 | 安装前端 `ui-dist` | 缺前端只回退到内置调试控制台，**不报错** |
| **4.5** | **预加载 USB 串口驱动**（写 `/etc/modules-load.d/gateway-serial.conf` + 立即 modprobe） | 见 §3.1 |
| **4.6** | **生成串口稳定名 udev 规则** + 打印映射表 | 见 §3.2 |
| 5 | 配置与模板落盘（**升级不覆盖** `config.json`） | 见 §4 |
| 6 | 设置权限（配置目录 `root:gateway`、目录需**组可写**） | |
| **6.5** | **写 journald 日志限额**（drop-in `/etc/systemd/journald.conf.d/60-gateway-journal.conf`）→ 重启 `systemd-journald` | 见 §2；重启 journald 失败不阻断安装，下次开机生效 |
| 7 | 装 systemd 服务（注入 `GATEWAY_WEB_DIR` / 时区 / OTA 分区）→ `daemon-reload` → `enable` → `restart` → 健康检查（最多等 30s） | 健康检查地址从 **`config.json` 的 `web.listen_addr`** 解析，不是环境变量 |

一条命令跑完上面全部（安装 → 等就绪 → 验证 → 导出检查单）：

```bash
sudo bash deliver.sh
```

分步执行（排障时用）：

```bash
sudo bash install.sh ./gatewayd ./ui-dist
sudo bash verify-deploy.sh
```

**健康检查失败时**：`install.sh` 末尾会提示诊断命令
`sudo journalctl -u gateway -n 50 --no-pager`。此时服务可能已经装了、只是没起来。

## 8. 装机后自检（`verify-deploy.sh`）

`verify-deploy.sh` 是**判定逻辑的唯一来源**，会生成可签字留档的 Markdown 检查单。
各段与本文的对应关系：

| 段 | 查什么 | 对应本文 |
|---|---|---|
| `[1]` systemd 服务 | unit 生效状态 | §7 |
| `[1b]` 时区 | 计划任务按**墙钟**解释 cron，时区错就是整体差 8 小时 | §9 |

## 9. 现场常见「看着正常其实没生效」速查

| 现象 | 最可能的原因 | 处置 |
|---|---|---|
| 服务正常、控制台能开，但**串口一条数据都没有**，日志无报错 | 驱动未加载 → 设备组解析失败 → `DeviceAllow` 整条丢弃 | §3.1，查 `/proc/devices` |
| 采集全线静默停摆，重启后更糟 | `port_name` 填了 `/dev/ttyUSB*`，重启后编号漂移 | §3.2，改用 `/dev/gateway-serialN` |
| 设备卡死**不会被硬件复位** | 看门狗候选路径没全放行 | §3.3 |
| DI/DO 输出无反应 | `/dev/gpiochip0` 未放行 | §3.3 |
| 网关**起不来**，日志说 `[security] refusing to start Web service` | 改了 `listen_addr` 但没设 `password_hash` | §5，倒回顺序 |
| 计划任务「每天 02:00」整体差 8 小时 | 精简镜像缺 tzdata，服务退化成 UTC | 设 `GATEWAY_TZ=+08:00` 或 `TZ=Asia/Shanghai` 后 `systemctl restart gateway` |
| OTA 升级失败 / 分区写不进去 | `DeviceAllow` 与 `GATEWAY_OTA_SLOT_*` 只改了一处 | §3.4，用环境变量重装 |
| 保存配置被拒（4021 / 7001 / 7003） | 无许可证时配额只有 100 点 | §6，先导许可证 |
| 日志把磁盘吃满，数据停采 | journald 无 `SystemMaxUse` 限额，与数据同盘（限额在 `journald.conf` 的 drop-in 里，不在 unit 里） | §2 |
| 断网几小时后历史数据**少了最旧的一段** | `queue.max_rows` 沿用默认 100 万行，撞上限后按 FIFO 淘汰最旧未送达行 | [`容量规划.md`](容量规划.md) §3.2 重算并改 `config.json`（改完要重启） |
| 前端打开是调试控制台 | `ui-dist/index.html` 没装上 | §1 |
