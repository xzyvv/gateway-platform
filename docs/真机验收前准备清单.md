# 真机验收前准备清单

> **定位**：[装机前准备清单](装机前准备清单.md) 回答「装之前要备什么」，本文回答「**执行真机验收前要准备什么**」。
> 目标：让 [linux-branch-review.md §4 真机验收表](linux-branch-review.md) 的 12 项 + [functional-inventory §C4](functional-inventory-and-next-roadmap.md) 的 3 条硬验收**一次完成**，不因缺设备 / 缺故障注入手段 / 缺签字单据而需要二次进场。
>
> 使用方式：出发前逐行核对 G/H/I/J/K 五组；到现场按 §6 顺序执行；判定与留档见 §3/§7；**离场后归档见 §10**。

---

## 0. 一分钟总览

| 组 | 内容 | 缺了会怎样 |
|---|---|---|
| **G** | 待验硬件与接线 | 硬件通路类验收项只能跳过，验收无法完成 |
| **H** | 故障注入能力（断网 / 断电 / 非 2xx 端点 / 可控 broker） | C4 三条（断电续传 / 死信重投 / 淘汰告警）全部无法验 |
| **I** | 判定与留档（交付包、检查单、诊断包、恢复介质） | 验收结果不被认可，或验收中损坏后无法恢复 |
| **J** | 人员与窗口 | 断电项需客户电气人员配合，缺人时只能停工等待 |
| **K** | 前置门禁（出发前自检） | 到现场后才发现交付包 / 证书 / 许可证不正确 |

## 1. G 组：待验硬件与接线

| 物项 | 规格 / 要求 | 用于验收项 | 提供方 |
|---|---|---|---|
| 目标 SKU 工控机 | 与交付清单同一型号、同一 eMMC/分区表；**不要用开发板替代** | 全部（尤其 OTA、性能基线） | 我方 |
| 可断电手段 | 带物理开关的插排或可编程电源；**不是 `poweroff` / `halt`** | C4.1 断电续传 | 我方 |
| 调试通道 | HDMI/串口 console + 键盘，或已确认可 SSH 且能进 bootloader | 恢复、OTA 回滚兜底 | 我方 |
| RS-485 从站 ≥ 1 台 | 真实电表/仪表；A/B 接线 + 120Ω 终端电阻；已知站号、波特率、寄存器表 | Modbus 实采、写超时、总线的错误分类 | 客户 |
| DI 4 路 / DO 4 路 | 开关、按钮、指示灯已接到端子并编号 | GPIO 无 EBUSY、输出翻转 | 客户+电气 |
| 4G 模块 + SIM | SIM 已激活、有流量、已贴号码；天线接好 | 4G 拨号、网络 failover | 客户 |
| USB 转串口线 | CP210x / CH340 / FTDI 各一（验稳定名规则覆盖度） | 串口稳定名（`serial-rules.sh` + udev） | 我方 |
| 网线 + 可插拔 WAN | 有线主链路 + 一个能物理拔掉的备用口 | 断网积压、failover | 客户 |
| U 盘（FAT32） | ≥ 8 GB，用于 OTA 包、日志与诊断包导出 | OTA 演练、留档 | 我方 |

> ⚠ 没有 RS-485 设备时，`verify-deploy.sh` 的硬件分组会给 WARN 而不是 FAIL（无设备 ≠ 通了），现场务必如实记录「未验」，不要当成通过。

## 2. H 组：故障注入能力（最容易遗漏的一组）

| 能力 | 具体准备 | 用于验收项 |
|---|---|---|
| 可控断电 | 见 G 组；提前与电气人员约定「直接拉闸」的动作与恢复人 | C4.1 |
| 可控断网 | 拔网线 / 关交换机口 / 防火墙 DROP；确认恢复方式 | C4.1、C4.3、failover |
| 可控 broker | 一台 mosquitto（可停、可限速、可踢连接），地址与端口已知 | C4.1 积压、MQTT 重连 |
| 可控非 2xx 端点 | 能返回 404/500 的 HTTP 服务（nginx 静态站点即可），可随时启停 | C4.2 死信重投 |
| 块设备写超时手段 | 现场一般不具备 —— **如无手段，明确写「未验」**，不要用 dd 把 eMMC 写坏 | OTA 写超时 |
| bootloader env 恢复手段 | 确认可进 U-Boot，或用 `fw_setenv` 能回写；**备份原 env 内容** | OTA 回滚判定 |
| 恢复介质 | 原始烧录镜像 + 烧录工具/SD 卡；OTA 演练前先备份整机镜像 | 全部（兜底） |

> ⚠ **OTA 演练的前提是「能救回来」**：破坏 `fw_env` 或写错分区后若无法恢复，设备将无法启动（变砖）。恢复介质未到位，OTA 项不开始。

## 3. I 组：判定与留档

| 物项 | 要求 |
|---|---|
| 交付包 | 与 CI 通过的那次提交一致；包内 `BUILD-INFO.txt` 的 `git_sha` 必须等于 `git rev-parse HEAD` |
| 验收脚本 | `deliver.sh` / `verify-deploy.sh` 取自**同一个包**，不要用本地旧版本（判定口径会不一致） |
| 检查单 | 打印 `verify-deploy.sh --report` 产出的 Markdown，含 PASS/FAIL/WARN 与判据；数据留存必须客户签字（`--retention-signed`） |
| 诊断留档 | 每次「不通过」或异常，导出 `GET /api/diagnostics/gateway`、`/api/diagnostics/logs/archives`、`/api/diagnostics/bus-load`、`/api/diagnostics/modbus-errors`、`/api/watchdog/services` |
| 证据材料 | 断电瞬间、DO 翻转、4G 路由切换、`systemctl status gateway` 各一段录屏或照片 |
| 回滚方案 | 恢复镜像 + 一条可执行的回退步骤（谁执行、多久） |

## 4. J 组：人员与窗口

| 角色 | 职责 | 备注 |
|---|---|---|
| 客户电气 | 接线、拉闸/送电、DO 负载 | 断电项必须本人在场 |
| 客户 IT | 网络/防火墙策略、SIM 与 APN、白名单 | failover 与 webhook 需要 |
| 客户签字人 | 数据留存边界、验收结论签字 | `--retention-signed` |
| 我方现场工程师 | 装机、验收、取证 | 熟悉 systemd 与 OTA |
| 我方远程支持 | 代码/日志判读 | 现场无网时可电话 |

- 窗口 ≥ **4 小时**，且包含**一次真实断电 + 一次重启**，避开生产时段。
- 若客户要求在生产网段直连，提前确认不会触发客户侧的安全告警。

## 5. K 组：出发前门禁（十分钟可完成）

```bash
# 1) 产包自检（不需要目标机）
sudo bash verify-deploy.sh --package-only

# 2) 产包与代码是否同源
git rev-parse HEAD
grep '^git_sha=' ./BUILD-INFO.txt

# 3) 清单类自检：装机前置是否齐（A~F 六组逐条）
grep -n '^## ' docs/装机前准备清单.md

# 4) 通行证：license 是否已签发并随包带入
ls -l license.json || echo "未签发：先按 docs/license-签发流程.md 取码再签"
```

- [ ] 交付包 `--package-only` 全部通过
- [ ] `BUILD-INFO` 的 sha 与本次 CI 通过的构建一致
- [ ] 目标机 root / sudo 免密方式已确认（密码 or 密钥）
- [ ] `password_hash` 已设置（否则只绑 127.0.0.1，现场访问不到）
- [ ] license 已签发 / 或现场取码流程已约定（含 mac/SN 取码命令）
- [ ] 恢复镜像与烧录工具已带

## 6. 验收项 → 准备物 → 判据

| # | 验收项 | 依赖 | 判据 | 参考 |
|---|---|---|---|---|
| 1 | 装机与基础检查单 | I | `deliver.sh` 执行完成，`verify-deploy.sh` 无 FAIL | 检查单 |
| 2 | 重启后自启 | G/J/I | `verify-boot.sh before` → reboot → `after` 全 PASS：boot_id 已变、开机后 ≤180s 进入 active、NRestarts 未增长、`/health/live` 200 | `verify-boot.sh` |
| 3 | 断电续传 | G/H | 直接拉闸 → 上电：已 commit 的行不丢，积压继续上送，无重复 | C4.1 |
| 4 | 死信重投 | H | 端点返回 404 → 重试按策略 → 进死信 → 恢复端点 → 重投成功且计数可查 | C4.2 |
| 5 | 队列淘汰告警 | H | 断网持续采集 → 达 `queue.max_rows` → 淘汰最旧 → 告警/指标可见 | C4.3 |
| 6 | GPIO | G | 无 `EBUSY`；4 路 DO 逐个翻转，万用表/指示灯一致 | §4 |
| 7 | 硬件看门狗 | G | 配置启用后能喂狗；进程被 `kill -STOP` 后按超时复位（**不复位时会变砖，先确认恢复介质**） | §4 |
| 8 | 优雅停机 | — | `systemctl stop` 后看门狗**不**复位、队列正常落盘 | §4 |
| 9 | 4G / 网络 failover | G/H | 拔主链路 → 切 4G → 数据继续上行；恢复后有回切，无静默断网 | §4 |
| 10 | 串口稳定名 | G | 三种 USB 串口线插拔后 `/dev/serial/by-id/...` 稳定，不出现 `ttyUSB` 漂移 | 装机清单 |
| 11 | 加密存储 | — | `encryption` 构建的包重启后可正常解密读历史；换 keyfile 拒绝启动且不毁库 | §4 |
| 12 | 主机指标 / 磁盘水位 | — | `/api/health/disk/history` 有数据；水位四档与实际占用一致 | 容量规划 |
| 13 | Modbus 写超时 | G | 从站不响应时写操作超时返回错误，不阻塞采集线程 | §4 |
| 14 | 心跳僵死检测 | — | 注入卡死任务后心跳判定生效、北向状态转「异常」 | §4 |
| 15 | OTA 全流程 | G/H/I | 升级→重启→版本正确；`fw_env` 破坏后判定失败并回滚到旧分区可用 | §4 ⚠ 手工 |
| 16 | 启动耗时基线（采数） | I | `timing --runs 3` 成功 ≥3 轮取中位数（服务级）；`after` 附带整机三段耗时。**首轮只记录不判定**，从第二轮起作为同版本包回归参照 | `verify-boot.sh timing` |

## 7. 现场执行顺序（半天版）

1. **装机**：`sudo bash deliver.sh`（非 eMMC 介质要带 `--ota-slot-a/--ota-slot-b`）→ 检查全部通过
2. **配置**：点位、北向、`api_token`、`password_hash`；保存后复查生成物
3. **硬件通路**：#6 / #10 / #13 / #12
4. **重启自启**：`sudo bash verify-boot.sh before --point <点位>` → `sudo systemctl reboot` → 上电后 `sudo bash verify-boot.sh after --report boot-after.md`（#2，含整机三段启动耗时）
5. **启动耗时基线**：`sudo bash verify-boot.sh timing --runs 3 --report boot-timing.md`（#16，会重启服务 3 次，避开断电/OTA 步骤）
6. **断电续传**：#3（拉闸前先记下已 commit 行数）
7. **OTA 演练**：#15（先备份镜像、先备份 env）
8. **断网 / 死信**：#5、#4、#9
9. **留档**：导出诊断包与检查单，客户签字，清理现场临时配置

## 8. 已知工具缺口（本次验收要手工兜住）

| 缺口 | 现状 | 现场替代做法 |
|---|---|---|
| 重启自启验证 | 已提供 `verify-boot.sh`（before/after 两阶段，含 boot_id、ActiveEnterTimestamp、NRestarts、数据留存核对）；但 CI 托管 runner 在 reboot 后即终止 job，无法自动化 | 现场执行两阶段脚本，`--report` 产物直接贴检查单 |
| 真机严格模式 | 无外设时硬件检查为 WARN，「没接」与「接了不通」判定不同 | 逐项在检查单上手写「未验 / 通过 / 失败」 |
| OTA 演练脚本 | CI 中 `fw_printenv` 缺失，A/B 检查恒为 DISABLED，无演练脚本 | 按 §4 手工执行，全程录屏 |
| 启动耗时基线 | 已提供 `verify-boot.sh timing`（服务级，N 轮取中位数）与 `after` 三段整机耗时（上电→active→ready）；首轮采数不判定 | 现场各跑一次，`--report` 产物记入该 SKU 首版基线，归档到 perf 文档 |
| ARM 目标 SKU 稳态基线 | `perf-baseline*` 为 CI/开发机口径；稳态 RSS/吞吐无 ARM 数据 | 现场采 30min 稳态 RSS 与采集吞吐，作为该 SKU 首版基线 |

## 9. 常见「准备不足」导致的表观失败

| 现象 | 真实原因 | 规避 |
|---|---|---|
| 4G 验收失败 | SIM 未激活 / 无 APN | G 组逐项确认 |
| 485 通信误码 | 缺终端电阻 / A-B 反接 | 带上 120Ω 电阻与万用表 |
| 断电续传「通过」得异常顺利 | 用的是 `poweroff` 而非拉闸，WAL 正常落盘 | H 组：必须是物理断电 |
| OTA 回滚后设备无法启动 | 没备份 env、没有恢复介质 | I 组：恢复介质先行 |
| 检查单与现场对不上 | 用了旧版 `verify-deploy.sh` | I 组：脚本与包同源 |
| 验收受阻于签字 | 数据留存未签字，检查单恒 WARN | J 组：签字人到场 |
| 前端无法打开 | `password_hash` 未设，只绑 127.0.0.1 | K 组门禁 |

## 10. 真机首跑归档步骤（离场后执行）

> 首跑与常规验收的区别：除了验收结论，还要产出**该 SKU 的首版基线**（启动耗时等）
> 并回写清单状态。基线只对**同版本交付包**有效，归档时必须与 `BUILD-INFO.txt`
> 的 `git_sha` 绑定，否则第二轮无法比较。

### 10.1 现场收集清单（离场前逐项核对）

| 产物 | 来源 | 缺失后果 |
|---|---|---|
| 检查单（含 PASS/FAIL/WARN） | `verify-deploy.sh --report` 产出，打印件客户签字后拍照/扫描 | 无签字 = 数据留存验收不被认可，回到 WARN |
| `boot-after.md` | `verify-boot.sh after --report boot-after.md`（含整机三段启动耗时） | 整机口径基线缺失，只剩服务级 |
| `boot-timing.md` | `verify-boot.sh timing --runs 3 --report boot-timing.md` | 服务级基线缺失 |
| `BUILD-INFO.txt` | 交付包内取 | 基线无法绑定版本，作废 |
| 证据材料 | 断电瞬间 / DO 翻转 / 4G 切换 / `systemctl status` 各一段（§3） | 事后争议无据可查 |
| 诊断包 | 仅异常场景：§3 列的 5 个诊断接口导出 | FAIL 项无法回溯定位 |
| 清单勾选原件 | 本文档 §6 十六项 + §9 实际发生的表观失败 | 未验项与真实原因遗失 |

### 10.2 归档目录与命名

```text
真机首跑-<YYYYMMDD>-<SKU型号>-<BUILD-INFO sha 前 7 位>/
├── checklist-report.md          # verify-deploy.sh 产出
├── checklist-signed.<jpg|pdf>   # 签字件
├── boot-after.md
├── boot-timing.md
├── BUILD-INFO.txt
├── evidence/                    # 录屏与照片，按验收项编号命名（#3-断电.mp4 …）
└── diagnostics/                 # 仅异常场景
```

### 10.3 回库后三个动作

1. **基线落库**：新建 `docs/perf-baseline-arm-<sku>.md`（格式对齐
   [perf-baseline-ci.md](perf-baseline-ci.md)），录入 `boot-timing.md` 的中位数与
   `boot-after.md` 的整机三段，**标题注明「v0 首轮采数，只记录不判定；同版本包第二轮起才作回归参照」**。
   稳态 RSS / 吞吐若现场采了 30min，一并录入；没采就写「待下轮」。
2. **状态回写**：[linux-branch-review.md §4](linux-branch-review.md) 的 12 项、
   functional-inventory §C4 三条、本文档 §6 十六项，逐项回写「通过 / 未验 / 失败」。
   **未验项必须写明原因**（缺设备 / 缺窗口），不允许留空——空着会被当成通过。
3. **问题转 issue**：FAIL 与 WARN 项逐条开 issue，正文引用证据文件名
   （`evidence/#7-看门狗.mp4`），不贴内网地址与设备 SN。

### 10.4 保密红线（本仓库为 public）

| 可入库 | 不可入库 |
|---|---|
| 基线数字（启动耗时、RSS、吞吐，不含设备标识） | 客户签字扫描件、诊断包原文 |
| 清单勾选结果与未验原因 | 内网拓扑 / IP / APN / broker 地址 |
| 已修复问题的 commit 链接 | 含产线环境的现场照片 |

签字件、诊断包、录屏原件存**公司内部归档系统**；仓库内对应文档只写一行
「原件已归档内部系统，编号 <X>」，保证可追溯即可。

### 10.5 首跑专项复盘（一轮 10 分钟）

- 清单本身好不好用：G~K 哪组漏了东西、§9 哪条应验了 / 没应验、哪条判据现场没法执行 →
  修订点直接改进本文档，不要攒。
- 工时记录：装机 / 配置 / 硬件 / 重启断电 / OTA / 留档各段实际耗时 → 修订 §7 的
  「半天版」承诺，避免下次窗口排错。
