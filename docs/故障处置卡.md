# 现场故障处置卡

本卡片面向现场运维/调试人员，覆盖网关上线后最常见的 6 类运行期故障。
每张卡按统一四段组织：**现象 → 判定 → 自愈/处置 → 恢复验证与数据完整性**。

配套自动化验证：`gateway-core/tests/chaos/scenarios.rs` 中 6 个同名场景
（`scenario_certificate_expired_*` / `scenario_license_expiry_*` /
`scenario_ntp_drift_*` / `scenario_watchdog_stall_*` /
`scenario_network_switch_*` / `scenario_southbound_long_silence_*`），
每次发版随混沌测试套件回归，防止处置路径退化。

## 通用取数入口

| 用途 | 入口 |
|------|------|
| 综合健康 | `GET /api/health/report` |
| 运行总览（总线/采集/队列） | `GET /api/diagnostics/gateway` |
| 北向通道状态 | `GET /api/north/status` |
| 指标（Prometheus 文本） | `GET /api/metrics` |
| 最近日志归档 / 下载 | `GET /api/diagnostics/logs/archives`、`GET /api/diagnostics/logs/download` |
| 配置快照 | `GET /api/config` |
| 总线负载 / Modbus 错误 | `GET /api/diagnostics/bus-load`、`GET /api/diagnostics/modbus-errors` |
| 守护服务与自愈事件 | `GET /api/watchdog/services`、`GET /api/watchdog/events` |

> 通用原则：**先取证再动手**。处置前保存上述响应（诊断包），
> 避免现场"恢复后无法复盘"。所有处置动作均需鉴权（token）。

## 卡 1：HTTPS 证书过期

**现象**
- 浏览器访问 Web 入口提示证书不受信任/已过期；设备侧 OTA 或北向 HTTPS 上报握手失败。
- 采集链路**不受影响**（证书只作用于 Web/北向安全通道）。

**判定**
- `GET /api/certificates`：`days_remaining ≤ 0` 即已过期（`-7 ~ 0` 为紧急，`≤ -1` 为过期）。
- `GET /api/health/report` 中证书项为 `Expired` 档。

**自愈/处置**
1. 生成新证书（CN/SAN 与现场访问域名或 IP 一致）。
2. `POST /api/certificates/upload` 上传新证书与私钥（或 `POST /api/certificates/renew` 走内置续签）。
3. 确认证书文件路径可读、私钥权限正确，必要时重启 Web 服务使新证书生效。

**恢复验证与数据完整性**
- `GET /api/certificates` 回到 `days_remaining > 30`（`Ok` 档），浏览器无告警。
- 数据完整性：证书过期期间采集与入队照常，历史/队列数据不丢；
  恢复后核对 `GET /api/health/report` 的队列深度与历史条数连续。

## 卡 2：License 到期 / 失效

**现象**
- Web 顶部提示授权到期或授权无效；超出配额的配置项被拒绝保存/新增。
- **采集主链路不中断**（过期只降级不阻断）。

**判定**
- `GET /api/license`：`status = Expired | Mismatch | Tampered | Invalid`，`present = false`。
- `get /api/status` / 健康报告中授权状态非 `Ok`。

**自愈/处置**
1. 记录 `license_id`、到期时间与机器指纹（`GET /api/license` 可见）用于续期申请。
2. `POST /api/license/import` 导入新 `.lic` 文件；返回成功且 `status = Ok`、`present = true`。
3. 若为 `Mismatch`：核对 license 绑定的机器指纹与现场设备是否一致（换板/换盘会导致指纹变化），
   按流程重新签发，不要手工改指纹。

**恢复验证与数据完整性**
- `GET /api/license` 回到 `Ok`，配额相关写操作恢复正常。
- 数据完整性：降级窗口内采集数据照常入队/落库；续期后按时间区间查询历史，
  降级窗口数据一条不少（对应 chaos 场景的「降级 + 恢复」双点校验）。

## 卡 3：NTP 失步 / 系统时钟回拨

**现象**
- 采集数据时间戳与现场时钟明显不一致，或历史曲线出现时间倒序。
- License 守卫报时钟异常，授权状态可能降级为 `Tampered`。

**判定**
- `GET /api/ntp/status`：同步状态异常、偏差超阈值。
- `GET /api/license`：`status = Tampered`（时钟回拨超过 48h 容差）。
- 日志出现 `clock rollback detected` 关键字。
- 日志出现 `system clock not trustworthy (...); scheduled tasks paused`：系统时间早于
  2020-01-01（无 RTC 掉电回退）或与最近一次 NTP 校时偏差超过 5 分钟，**计划任务已暂停**，
  避免在错误时刻执行；手动「立即执行」不受影响。

**自愈/处置**
1. 检查上游 NTP 服务器可达性与防火墙（UDP 123）。
2. `POST /api/ntp/sync` 触发一次校时；确认 `GET /api/ntp/status` 恢复同步。
3. 校时成功后，License/时钟守卫的基准会被重置（`ClockGuard::resync`），状态回到 `Ok`。
4. 严禁手动把系统时间往前调（会再次触发回拨判定）。
5. 系统时间恢复可信后，调度器会自动按当前时刻重排全部启用任务（日志
   `scheduled tasks re-anchored`）；**时钟不可信期间漏掉的窗口不补跑**，属预期行为。

**恢复验证与数据完整性**
- `GET /api/ntp/status` 正常，`GET /api/license` 回 `Ok`。
- 数据完整性：失步窗口的数据仍按采集时刻落库，不因校时被丢弃或改写；
  校时后核对 `GET /api/diagnostics/logs` 与历史区间，确认无缝衔接。

## 卡 4：采集循环卡死（看门狗触发）

**现象**
- 某设备/总线的数据停止刷新，但进程与 Web 仍在运行。
- 日志出现 `WATCHDOG: loop '<name>' became stale`。

**判定**
- `GET /api/watchdog/services`：对应循环状态 `stale`，滞后毫秒数持续增长。
- `GET /api/metrics`：`gateway_watchdog_timeouts_total` 增加。
  注意该计数为**边沿触发**：一次卡死只 +1，不会随卡死时长刷屏。
- `GET /api/watchdog/events` 可看到自愈/重启事件。

**自愈/处置**
1. 先取证：保存 `/api/watchdog/services`、`/api/diagnostics/gateway`、最近日志。
2. 由守护服务自动重启对应采集任务（`POST /api/watchdog/services/{name}/restart` 可手动触发）。
3. 若反复卡死：检查该总线的设备响应、协议参数（超时/重试）、以及是否存在超大 Lua 脚本。

**恢复验证与数据完整性**
- 循环恢复 kick 后 `stale_loops` 清空，`/api/watchdog/services` 状态回到正常。
- `gateway_watchdog_timeouts_total` 不再继续增长（同一次卡死不再重复计数）。
- 数据完整性：卡死窗口内已入队的数据不丢；恢复后历史曲线仅出现「空窗」而无缺口错位。

## 卡 5：承载网络切换（4G/有线切换、链路闪断）

**现象**
- Modbus TCP / IEC104 / MQTT 等通道短时全部或部分失败，随后自动恢复。
- 采集值不应出现「旧值冒充新值」：断网期间数据质量应为 `Bad`。

**判定**
- `GET /api/diagnostics/gateway` 显示对应总线/设备连接失败或重连中。
- `GET /api/north/status` 北向通道 `disconnected` / 重连退避中。
- 日志出现连接被关闭/重连退避关键字。

**自愈/处置**
1. 确认物理链路（网线/4G 信号/路由）与目标地址可达性（现场可用协议工具探测）。
2. 网关按 `reconnect_backoff` 自动重连，一般无需人工重启；等待退避周期结束即可。
3. 若长时间不恢复：核对目标 `tcp_addr`/端口、现场防火墙策略，确认后手动重启对应总线任务。

**恢复验证与数据完整性**
- 下一次采集恢复正常值且质量 `Good`；`/api/north/status` 回到已连接。
- 数据完整性：断网期标记 `Bad` 的点与恢复后的 `Good` 点都应保留在队列/历史中，
  不得因重连丢点；对应 MQTT Outbox 会在重连后补发。

## 卡 6：南向设备长时无响应

**现象**
- 单个从站/仪表长时间不回帧（设备断电、接线松动、波特率/站号错配）。
- 总线上该设备的读取持续超时报错，但不拖垮其他设备。

**判定**
- `GET /api/diagnostics/bus-load`：该总线错误率/超时数上升。
- `GET /api/diagnostics/modbus-errors` 与 `/issues`：可见超时/无应答分类。
- 日志出现 `NoReply` / 超时 / 重试关键字；单次读取耗时接近「超时 × (重试+1)」。

**自愈/处置**
1. 现场检查：供电、A/B 线序与终端电阻、站号、波特率/校验位、地址是否越界。
2. 用协议工具（发帧/探测）单独验证该从站是否可应答；不可达时属现场设备问题，网关只如实报错。
3. 确认设备恢复后，无需重启总线，下一笔事务会自动成功。

**恢复验证与数据完整性**
- 该点恢复刷新，质量 `Good`；同总线其他设备不受影响。
- 数据完整性：静默窗口的点标 `Bad` 保留，恢复点正常入库；
  不得出现「静默期伪造成功值」或「恢复后历史缺口」。

## 处置记录要求

每次现场处置至少记录：

1. 故障卡编号 + 发生时间 + 恢复时间；
2. 处置前诊断取证（健康报告 / 相关状态接口 / 日志片段）；
3. 实际执行的处置动作与结果；
4. 恢复后数据完整性核对结论（窗口内数据是否齐全、质量位是否正确）；
5. 若为首次出现的新故障形态：按 `gateway-core/tests/chaos/README.md`
   的约定补一个 `scenario_*` 回归场景。
